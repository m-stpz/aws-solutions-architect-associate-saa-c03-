# S3 Encryption

We can encrypt objects in s3 buckets using 1 of 4 methods

- 3 being server-side
- 1 being client-side

## Server-side encryption[SSE]

Server-side encryption comes in 3 types

1. SSE-S3: managed by s3
2. SSE-KMS: uses Key Management Service
3. SSE-C: customer-provided keys

### 1. SSE-S3: uses amazon s3-managed keys [enabled by default]

- encrypts s3 objects using keys handled, managed, and owned by AWS
  - we don't have access to this key

- encryption type is AES-256
- must set header `"x-amz-server-side-encryption":"AES256"`
- enabled by default for new buckets and new objects

```
        http[s] + header  | amazon s3                                   |
user -----> upload ------>| object  ----- [encryption] ----> s3 bucket  |
                          | + s3 owned key                              |
```

### 2. SSE-KMS: uses KMS keys stored in AWS KMS

- leverages AWS Key Management Service [AWS KMS] to manage encryption keys
- advantages:
  - user control + audit key usage using CloudTrail
- must set header `"x-amz-server-side-encryption:"aws:kms"`

```
        http[s] + header  | amazon s3                                   |
user -----> upload ------>| object  ----- [encryption] ----> s3 bucket  |
                          | + AWS KMS [kms key]                         |
```

#### SSE-KMS Limitation

> Since we need to make API calls for this service, its limit-usage can cause unintended consequences

- We can be impacted by the KMS limits
  - we need to make API calls for KMS key
- When you `___`, it calls the `____` KMS API
  - upload / GenerateDataKey
  - download / Decrypt
- These operations count towards the KMS quota per second
  - 5,5k, 10k, 30k req/s based on region
- We can request a quota increase using the Service Quotas Console

```
  s3 bucket <-- api call --> KMS Key
  |
  | [upload/download SSE-KMS]
  users
```

#### DSSE-KMS

> New option available, it's `DSSE-KMS`, it means **double encryption based on KMS**

### 3. SSE-C: uses Customer-provided keys

- when you want to manage your own encryption keys
- server-side eencryption using keys fully managed by the customer OUTSIDE of AWS
- S3 does NOT STORE the provide encryption key
- Since the key is present on the requests, **HTTPS must be used**
  - encryption key is provided in the HTTP headers, for EVERY HTTP request made

```
        https only        | amazon s3                                   |
user -----> upload ------>| object  ----- [encryption] ----> s3 bucket  |
        + key in header   | + [client provided key]                     |
```

> It can't be done from the console/UI, only from the CLI

## 4. Client-side encryption

- The 4th type is not server-side, but client
- Use client libs such as Amazon S3 client-side encryption library
- Client must `____` data themselves `____` Amazon S3
  - encrypt / before sending it to
  - decrypt / when retrieving it from
- Customer fully managed the keys and encryption cycle

```
file                                                      | amazon s3
+ ---> [encryption] ---> file ----> [upload HTTP(s)] ---> | amazon bucket
client key               encrypted                        |
```

> You need to do everything client-side, so you don't need to tell AWS about it

## Encryption in transit [SSL/TLS]

- Encryption in flight is also called SSL/TLS
- Amazon S3 exposes two endpoints:
  - HTTP: not encrypted
  - HTTPS: encryption in flight

- HTTPS is recommended
  - mandatory for SSE-C
  - most clients would use the HTTPS endpoint by default

- How do you force encryption in transit?
  - `aws:SecureTransport`
  - you add a statement that blocks any question in which `aws:SecureTransport` is false

```
user ---> http ---> [❌ blocked] --- | aws
user ---> https ---> [✅ accepted]-- | s3 bucket [with bucket policy]
```

## Hands on

- Amazon s3 / buckets / create bucket
- Scroll to encryption
  - select one type
    - SSE-S3 / SSE-KMS / DSSE-KMS
- After creating this encrypted bucket, once we upload a file, and we check its encryption, it will appear under `encryption type`

> If you encrypt an object with a given encryption type and after you want to change it, it will create a new version of the object. Thus, versioning should be enabled

## Default Encryption

- SSE-S3 encryption is automatically applied to new objects stored in s3 bucket
- Optionally, we can "force encryption" using a bucket policy and refuse any API call to PUT an S3 object without encryption headers
  - [SSE-KMS or SSE-C]

> Bucket policies are evaluated before `Default Encryption`

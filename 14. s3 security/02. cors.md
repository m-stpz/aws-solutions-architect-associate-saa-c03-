# S3 Cors

- CORS: Cross-Origin Resource Sharing
  - origin: protocol + domain + port
    - ex: `https://example.com`
      - implied port: 443 https / 80 http
- It's a web browser mechanism to allow/reject requests to other origins while vising the main origin
  - same origin: `http://example.com/app1` and `http://example.com/app2`
  - different origin: http://example.com` and `http://other.example.com`
- Request won't be fulfilled unless the other origin ALLOWS for the requests, using the **CORS Headers** [ex: `Access-Control-Allow-Origin`]

```
[ Web Server (Origin) ]                 [ Web Browser ]                 [ Web Server (Cross-Origin) ]
https://www.example.com                                                 https://www.other.com
         │                                     │                                  │
         │◄───────── HTTPS Request ───────────►│                                  │

         │                                     │◄─ Access-Control-Allow-Origin:   │
```

## Core Problem CORS solve

- By default, browsers enforce the Same-Origin Policy
  - if a user visits your website [http://my-app.com] and your frontend JS tried to fetch something [image/font/video] from an S3 bucket [https://bucket.s3.amazonaws.com]
  - the browser will BLOCK the response UNLESS the S3 bucket EXPLICITLY allows this via CORS headers

- CORS only matters when the web browser ITSELF is the one making the request to the cross-origin server
  - if server1 makes the backend-to-backend request to server to, CORS doesn't exist and is ignored
  - browser needs to talk directly to server2

```
1. web browser does request server 1
2. server1 instructs browser to grab stuff on server2
    - server1 = origin
    - server2 = cross-origin
3. server2 must allow cors, else the browser blocks it?
    - check CORS rules: is server1 allowed?
    - server2 must ALLOW `server1`
```

> A script running on domain A is forbidden from reading responses returned by domain B

## How S3 Evaluates CROS

- When a cross-origin request is made to S3, it checks the CORS config XML/JSON file
- S3 cors config consists of a set of rules, which contain:
  - AllowedOrigins: which external domains are permitted to access the bucket
    - ex: `https://*.example.com` or `*`
  - AllowedMethods: which HTTP methods are allowed
  - AllowedHeaders: which request headers the client is allowed to send
  - ExposeHeaders: which custom headers S3 is allowed to send back that the browser JS can read
  - MaxAgeSeconds: how long [in seconds] the browser can cache the preflight response, so it doesn't have to send an `OPTIONS` request before every single fetch

> CORS is configured PER bucket
> CORS doesn't replace bucket policies or IAM

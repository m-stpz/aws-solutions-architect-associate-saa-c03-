# Aurora

- Compatible API for postgresql/mysql
- Separation of storage and compute
  - storage: data is stored in 6 replicates, across 3 AZs
    - highly available, self-healing, auto-scaling
  - compute: cluster of db instance across multiple AZ, auto-scaling of read replicas
  - cluster: custom endpoints for writer and reader DB instances
- Same security, monitoring, maintenance features as RDS
- Aurora serverless: for unpredictable, intermittent workloads, no capacity planning
- Aurora global: up to 16db read instances in each region, < 1s storage replication
- Aurora machine learning: perform ML using SageMaker and Comprehend on Aurora
- Aurora db cloning: new cluster from existing one, faster than restoring a snapshot

- Use case: smae as RDS, but with less maintenance, more flexibility, more performance, more features

## Aurora vs RDS

Aurora is technically part of the RDS family, however, it has different bells and whistles

| Feature          | RDS                                                          | Aurora                                                                |
| ---------------- | ------------------------------------------------------------ | --------------------------------------------------------------------- |
| Engines          | postgres, mysql, mariadb, oracle, sql server, ibm db2        | postgres, mysql                                                       |
| Underlying infra | traditional monolithic db instance attached to an EBS volume | decoupled compute and storage                                         |
| Storage scaling  | Pre-allocated, bu can auto-scale                             | Auto expands in 10gb, up to 128tb. shrinks when data is deleted       |
| Read replicas    | max 5; uses traditional async binlog/WAL replication         | up to 15 read replicas sharing the same underlying dist. storage vol. |
| Replication lags | varies from ms to minutes                                    | near-zero because replicas read the same shared storage               |
| Failover time    | ~60-120s                                                     | < 30s                                                                 |
| Baseline cost    | lower entry cost                                             | ~20% more expensive on compute baseline; charges per IOPS/req vol     |

So, it means that Aurora:

- has decoupled storage and compute
- auto-scales and shrinks independently
- has more read replicas
- has less replication and failover time
- is, in general, more expensive

When to pick:

- RDS
  - db engine other than postgres/mysql
  - tight budget or operating dev/test/staging environments
  - write throughput and connection concurrency is modest and steady

- Aurora
  - production postgres/mysql with high transactions per second [OLTP]
  - need fast auto-scaling read capacity
  - high availability and minimal recovery time are needed
  - traffic patterns more volatile and unpredictable

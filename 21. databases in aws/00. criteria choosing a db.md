# 4 dimensions when choosing a db

These 4 dimensions are the core engineering criteria used to evaluate, select, and design any persistence layer or distributed system

- data structure: the shape of the data. How is the data organized?
  - relational, key-value, document, graph, append-only, object
- access patterns: how the system reads/writes. What's the read/write ratio? What's the consistency needed?
  - read-to-write, known lookups vs. ad hocs, consistency requirements [ACID vs. BASE], batch vs operational
- latency targets: how fast should the response be
- scaling model: how we handle growth

## 1. Data structure: shape of the data

how the info is physically organized, constrained and related in memory an on disk

- relational/tabular: fixed schemas composed of rows + columns
  - strict data types
  - entities reference each other through pk and fks
  - ex: postgresql, mysql, aurora

- key-value: value associated with a lookup key
  - highly performance because lookups resolve to direct hash-table addresses
  - ex: redis, dynamodb

- document [hierarchical/semi-structured]: self-describing nested formats, like JSON or BSON
  - data that belongs together is embedded together
  - order with its line items and shipping address stored in one document
  - ex: firebase, mongodb

- graph [nodes/edges]: entities connected by relationships with properties on both
  - ex: neptune

- time-series/append-only: append-only records where time is the primary dimension
  - data arrives sequentially, rarely updated and optimized for range queries and downsampling
  - ex: timestream

- object/blob: unstructured byte streams of general size with attached metadata
  - ex: s3

## 2. Access patterns: how the system reads and writes

Describe queries, mutation workflows and consumption behavior against the data

- read-to-write ratio:
  - read-heavy: 95:5
    - blogs, product catalogs, social feeds
    - optimal for aggressive caching [cloudfront, elasticache, dax]
  - write-heavy: 20:80
    - IoT metrics, financial transaction ledgers, clickstream trackers
    - append-only logs, queue buffering [SQS, kinesis], or LSM-tree dbs

- known point lookups vs. ad-hoc queries:
  - known lookups: querying strictly by known keys [ex: `Get user where id = 123`]
    - NoSQL is great for it
  - Ad-hoc exploratory queries: querying by arbitrary combinations of columns, ranges and joins
    - requires SQL

- consistency requirements
  - strong consistency [ACID]: banking ledgers, inventory decremeting, payment systems
    - requires transactional locks and serialized write logs
  - eventual consistency [BASE]: social media likes, comment feeds, email subscriber lists
    - allow data replication to catch up seconds later
    - lower latency and higher availability

- batch vs. transactional [OLAP vs. OLTP]:
  - OLTP [online transaction processing]: high-frequency, low-latency reads and writes of single rows and small sets
    - ex: checkout workflows
  - OLAP [online analytical processing]: scans of millions of historical rows, aggregating sums, averages, and group-bys
    - ex: data warehosing

## 3. Latency targets: how fast responses must be delivered

Define the maximum tolerable round-trip duration for a data op, usually measured in percentiles [p50, p95, p99]

| Time                                   | DB                                                                                 | Use case                                                              | implementation detail                                                |
| -------------------------------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------- | -------------------------------------------------------------------- |
| microsecond [< 1ms]                    | in-memory store, elasticache [redis], local RAM cache                              | session caches, gaming leaderboards, high-frequency trading           | disk access eliminated, data lives in RAM                            |
| single-digit ms [1-9ms]                | operational nosql & OLTP dbs, dynamodb, Aurora/RDS [primary key index], documentdb | standard benchmark for web and mobile apis                            | data is retrieved from local SSDs via indexed b-tres/hash partitions |
| tens to hundreds of ms [10ms - 100+ms] | object storage and scans, s3, full table scanes / athena, cross-region db calls    | complex relational joins, disk-heavy scans, cold object fetch from s3 |                                                                      |

## 4. Scaling model: how the system handles growth

How the persistence layer adapts when data volume, query concurrency, or throughput expands by orders of magnitude

| Model                                       | Mechanics                                                                                                                                      | Used by                         | Observations                                                                                          |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Vertical scaling [scale-up]                 | increasing physical hardward capacity of a single server [more CPU/RAM/IOPS]                                                                   | traditional RDS                 | hard hardware limits, high fixed costs, possible downtime                                             |
| Horizontal scaling [scale-out/partitioning] | data and query are spread across multiple independent nodes using a hash algo on a part key                                                    | dynamodb, cassandra, mongodb    | virtual infinite scaling / multi-partition transaction and cross-partition joins expensive/impossible |
| Read-write decoupled scaling                | directing all mutating traffic [mutation] to a single writer node, while fanning out read [query] to an auto-scaled pool of read-only replicas | aurora [up to 15 read replicas] | single-writer bottleneck, replication lag                                                             |
| Serverless [on-demand elastic scaling]      | compute and storage are decoupled. storage expands per gb, compute per incoming req throughput                                                 | dynamodb on-demand              | higher unit cost per req, pay per request                                                             |

# Choosing the right db

- It comes down to:
  - data structure
  - access patterns
  - latency targets
  - scaling model

> For more info see `databases in aws/00. criteria choosing a db`

Questions to choose the right db based on your architecture:

- Read-heavy, write-heavy, or balanced workload?
- What's the throughput need? Will it change, does it need to scale/fluctuate during the day?
- How much data to store and for how long? Will it grow?
  - average object size?
  - how are they accessed?
- Data durability? Source of truth for the data?
- Latency requirements? Concurrent users?
- Data model? How will you query the data?
  - joins? structured? semi-structured?
- Strong schema? More flexibility? Reporting? Searching? RDBMS/NoSql
- License costs? Switch to cloud native db such as Aurora?

## Db Types

- RDBMS [SQL/OLTP]: great for joins
  - RDS, Aurora
- NoSQL db - no joins, no SQL
  - dynamodb [json]
  - elasticache [key/value pairs]
  - neptune [graphs]
  - documentdb [for mongodb]
  - keyspaces [apache cassandra]
- Object store:
  - S3 [big objects]
  - glacier [backups/archives]
- Data warehouse [sql analytics/BI]
  - redshift [OLAP]
  - athena
  - EMR
- Search: free text, unstructured searches
  - OpenSearch[json]
- Graphs: displays relationships between data
  - neptune
- Ledger: quantum ledger db
- Timeseries: amazon timestream

## Sum up

| Service      | Core data model                                                | scaling and architecture                                                                              | Main user cases                                                                                                                                   |
| ------------ | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| RDS          | Relational SQL [Postgres, MySQL, Oracle, SQL Server, Maria db] | Vertical scaling + trad. EBS storage; max 5 read replicas; multi-AZ for failover                      | Traditional web application backends; entreprise apps requiring oracle/sql server; lift-and-shift migrations from on-prem SQL dbs                 |
| Aurora       | Relational SQL [Postgres, MySQL]                               | Cloud-native distributed storage; auto-expands to 128tb; up to 15 read replicas; Aurora serverless v2 | High-throughput e-commerce dbs; mission critical relational workloads; multi-region global applications requiring active-active or fast DR        |
| DynamoDB     | NoSQL key-value & document [json]                              | True serverless; horizontal auto-partitioning via partition/sort keys; scales infinitely              | Serverless web and mobile backends; e-commer shopping carts and catalog metadata; high-velocity event-tracking and gaming state management        |
| ElasticCache | In-memory key-value [redis/valkey/memcached]                   | In-memory cluster nodes; horizontal scaling via sharding [Redis] or nodes [memcached]                 | Relieving db CPU/connection bottlenecks; user session storage and management; real-time leaderboards; pub/sub messaging, and caching freq queries |
| S3           | Object /blob storage                                           | Virtually infinite capacity; automatic horizontal scaling across multiple AZs                         | Static website hosting and media assets; big data analytics data lakes [queried via Athena]; backup, archival, and DR repos                       |
| DocumentDB   | Document JSON/BSON                                             | Decoupled storage [scales up to 128tb]; fully managed cluster instances                               | Content and catalog management; user profiles and metadata catalogs; applications requiring flexible, nested JSON schemas                         |
| Keyspaces    | Wide-column NoSQL [Apache Cassandra compatible]                | Serverless, distributed, multi-region architecture built on top of Cassandra APIs                     | Large-scale industrial data-ingestion; high-velocity messaging platforms; workloads dependent on Cassandra query patterns                         |
| Neptune      | Graph                                                          | Managed graph cluster with read replicas sharing a distributed storage volume                         | Fraud detection rings; recommendation engines; social networks and identity graph mapping                                                         |
| Timestream   | Time-series [Append-only timestamped events]                   | Serverlessl automatic data tiering between an in-memory store and a cost-optimized magnetic store     | IoT device sensor telemetry; application performance monitoring [APM]; DevOps server metrics and fleet tracking                                   |

# CloudFront

- Content Delivery Network [CDN]
- Improves READ performance, content is CACHED at the edge
  - improves user experience
  - reduces latency
- Hundreds of points of presence globally
  - edge locations, caches
- DDoS protection [because it's worldwide], integration with Shield, AWS Web Application Firewall

## Origins

- S3 Bucket
  - for distributing files and caching them at the edge
  - for uploading files to s3 through CloudFront
  - secured using Origin Access Control [OAC]

- VPC origin
  - for applications hosted in VPC private subnets
  - private application load balancer / network load balancer / ec2 instances

- Custom origin [HTTP]
  - S3 website -> must first enable the bucket as a static S3 website
- Any public HTTP backend you want
  - example: public ALB

### Origin Access Control [OAC]

- Security feature for CloudFront
- Secures the communication between CloudFront dist and origin server
  - most commonly Amazon S3 bucket

## CloudFront vs S3 Cross-Region Replication

- CloudFront [CDN]
  - global edge network
  - files are cached for TTL [maybe a day]
  - great for STATIC content that must be available everywhere

- S3 Cross-Region Replication [CRR]
  - must be setup for each region you want
  - files are updated near real-time
  - read only
  - great for DYNAMIC content that needs to be available at low-latency and fresh in few regions

| Feature            | CloudFront                                                                 | S3 Cross-region replication                                                             |
| ------------------ | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Main goal          | low-latency global content delivery to end-users                           | data durability, DR and compliance                                                      |
| Architecture layer | edge layer [caches files globally across 100s of points of presence]       | storage layer [replicates data directly bucket-to-bucket between AWS regions]           |
| Target audience    | web browsers, mobile apps, and end-users requesting static/dynamic content | regional application servers, data pipelines, or backup systems requiring regional data |
| Data scope         | caches only what users request                                             | replicate entire buckets or subsets sync/async across regions                           |
| Failover and DR    | not a backup storage solution                                              | great for DR                                                                            |

## Hands on - CloudFront with S3

1. Create bucket
2. Upload the necessary files
3. Go to cloudfront
4. Select plan
5. Select distribution type
   - single website/app
   - multi-tenant architecture
6. You can add a domain
7. Origin type: where the content lives
   - s3, elb, API gateway, elemental mediapackage, other
   - in this case, we selected `s3`
   - then select the bucket
8. Once, we do that, it's add the permissions to the s3
   - even though the files are private, CloudFront will allow us to share them publicly

## CloudFront - ALB/EC2 as origin

### Recommended: Using VPC origins

- Allows to deliver content from applications hosted in VPC private subnets
  - no need to expose them on the internet
- Deliver traffic to private:
  - application load balancer
  - network load balancer
  - EC2 instances

```
                            | [VPC]                             |
users ----> CloudFront ---->| VPC Origin    | [Private subnet]  |
                            |     |------>--| NLB               |
                            |     |------>--| ALB               |
                            |     |------>--| EC2 instance      |
```

- VPC Origin is the interface that allows CloudFront to connect to items within our private subnet

### Old way: Using public network

```
                        [allow public IP of edge locations] | [security group]
users ---> edge location ---------------------------------- | ec2 instances
                                                            | [must be public]

                         [allow public IP of edge locations]  | [security group] | [allow security group of load balancer] | [security group]
users ---> edge location ------------------------------------ |  ALB             | ----------------------------------------| EC2 instances
                                                              | [must be public] |                                         | [can be private]
```

## Geo Restriction

- We can restrict who can access the distribution
  - allowlist: allow users to access content ONLY IF they're in one of the countries that's in the APPROVED list
  - blocklist: block users to access content IF they're in one of the countries that's in the BANNED list

- The "country" is determined using a 3rd party geo-ip database
- Use case: copyright laws to control access to content

### Hands on geo restriction

- On CloudFront / distributions / <specific-distribution>
  - it might need to be pay as a you go type of CDN
- Security / CloudFront geographic restrictions
  - no restrictions | allowlist | blocklist

## Cache invalidation

- In case we update the back-end origin, CloudFront doesn't know about it and will only get the refreshed content after the TTL has expired
- We can force an entire or partial cache refresh, thus bypassing the TTL, by performing a CloudFront invalidation
- We can invalidate all files (`*`) or a special path (`/images/*`)

# SNS (Simple Notification Service)

- SNS: sending one message to MANY receivers
- Producer sends message to ONE SNS TOPIC
- A topic can have N subscribers on the topic
- Each sub to the topic will get all the messages
- Up to 12,5M subscriptions per topic
- 100k topics

```
SNS ---- publish ----> Subscribers
                    - SQS, Lambda, Kinesis Data Firehose, emails, SMS/mobile notifications, HTTP endpoints
```

- SNS receives data from many AWS services

```
Services    -------------------------- publish -----------------------> SNS
- CloudWatch alarms, ASG notifications, CloudFormation, AWS budget
- S3 bucket [events], AWS DMS [new replic], Lambda, DynamoDb, RDS events
```

## How to publish

- Topic publish [using the SDK]
  - create topic
  - create 1/N subscription
  - publish to the topic

- Direct publish [for mobile apps SDK]
  - create platform application
  - create platform endpoint
  - publish to the platform endpoint
  - works with Google GCM, apple APNS, amazon ADM

## Security

- Similar to the SQS security

- Encryption
  - in-flight encryption using HTTPS API
  - at-rest encryption using KMS keys
  - client-side encryption if the client wants to perform encryption/decryption itself

- Access controls: IAM policies to regulate access to the SNS API

- SNS access policies:
  - useful for cross-account access to SNS topics
  - useful for allowing other services [S3...] to write to an SNS topic

## SNS vs. SQS

- Both SNS and SQS are both managed messaging services, they are however, built on different communication models
  - Simple Notification Service vs. Simple Queue Service
  - Notification vs. Queue
    - Notification: Pub/Sub [push]
    - Queue: Message queueing [pull]

- SNS: Radio broadcast station [Push / 1-to-many]
  - instant transmission
  - many listeners [fan-out]: tune in into the frequency
  - ephemeral [no buffer]: if radio is off when the song plays, you miss it

- SQS Postal mailbox [Pull / 1-to-1]
  - durable storage: the letter stays there until you open it
  - pull-based: you need to go outside and pick it up
  - single consumer: once you your letter, it's yours. Other people can't take it
  - Pacing: if N letters arrive, you can open them little by little

```
SNS [Pub/Sub - Push]
Producer ---> [SNS Topic] ---- Push --> HTTP/Webhook
                            |- Push --> Lambda
                            |- Push --> SQS queue A
                            |- Push --> SQS queue B

SQS [Queue - Pull]
Producers --> [SQS Queue] <--- Poll [pull] -- Consumer A
                          <--- Poll [pull] -- Consumer B
```

- SNS pushes messages
  - when a publisher sends a message to an SNS topic, they are delivered across ALL SUBSCRIBED ENDPOINTS
  - if no sub exists, or if a direct HTTP endpoint id down and the retries fail, the message is lost
    - unless backed by a dead-letter queue or persistent store

- SQS holds message until pulled
  - producer places a message in the queue
  - message stays there until a consumer polls the queue to fetch, process, and delete it

### SNS and SQS: Fan out pattern

- One of the most foundational patterns in distributed systems and event-driven architecture on AWS
  - broadcast capability: pub/sub, SNS
  - durability, load leveling and retry safety: Queue, SQS
- In microservice architecture, you frequently combine both services

```
                      +-------------------+
                      |   Order Service   |
                      +-------------------+
                                |
                                | (Publishes "OrderPlaced")
                                v
                      +-------------------+
                      |  SNS Topic        |
                      |  "order-events"   |
                      +-------------------+
                       /        |        \
                      /         |         \  (Fan-out delivery)
                     v          v          v
              +-----------+ +-----------+ +-----------+
              | SQS Queue | | SQS Queue | | SQS Queue |
              | (Billing) | |(Inventory)| | (Shipping)|
              +-----------+ +-----------+ +-----------+
                    |             |             |
                 Worker        Worker        Worker
```

Why use it?

- Only SQS queue? Then service would need hard-coded knowledge of every downstream service
- Only SNS? Then data loss could happen if some downstream consumer was down
- With both
  - SNS brodcast to the topic
  - SQS queue being subscribed to the topic will receive it and guarantee data persistence

- Push once in SNS, receive in all SQS queues that are subscribers
- Fully decoupled, no data loss
- SQS allows for:
  - data persistence, delayed processing, retries of work
- Ability to add more SQS subs overtime [broadcast capability given by SNS]
- SQS queue access policy must allow for SNS to write
- Cross-region delivery: works with SQS queues in other regions

#### Use cases for the SNS + SQS: fanout pattern

1. S3 events to multiple queues

- sending the same s3 event to many SQS queues, use fan-out

```
                                                sqs queues
                events                         / []
s3 object created ----> S3 ----> SNS topic ----- []
                                               \ lambda function // not only the SQS queues can be included in the topic subscription
```

2. SNS to s3 through Kinesis Data Firehose [KDF]

- SNS can send to Kinesis and therefore we can:

```
Service ---> SNS TOPIC ----> KDF ----> S3
                                    \ Any supported KDF destination
```

## SNS - FIFO

- Ordering of messages in the topic

```
        send messages  receive messages
publisher ---------> SNS ----------> Subscriber [SQS FIFO]
         4 3 2 1          4 3  2  1
```

- Similar features as SQS FIFO
  - ordering by message group ID [all messages in the same group are ordered]
  - deduplication using a deduplication ID or content-based deduplication
- Can have SQS standard and FIFO queues as subscribers
- Limited throughput [same throughput as SQS FIFO]

### SNS FIFO + SQS FIFO: Fan out pattern

- In case we need: fan out + ordering + deduplication

```
                            SQS FIFO Queues
Service1 --- SNS FIFO Topic ----> [] ----> Service2
                                \ [] ----> Service3
```

## Message filtering

- JSON policy used to filter messages sent to SNS topic's subscriptions
- If a subscription doesn't have a filter policy, it receives every message

```
Service -----> SNS topic ---- [filter policy: placed] ----> SQS queue [placed orders]
                          |-- [filter policy: cancelled] ----> SQS queue [canceled orders]
                          |                     | --------> email subscription [canceled orders]
                          |---- [filter policy: declined] ----> SQS queue [declined orders]
                          ----- SQS queue [all]
```

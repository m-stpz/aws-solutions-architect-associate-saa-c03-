# SNS (Simple Notification Service)

- SNS: sending one message to MANY receivers
- Producer sends message to ONE SNS TOPIC
- A topic can have N subscribers on the topic
- Each sub to the topic will get all the messages
- Up to 12,5M subscriptions per topic
- 100k topics

```
SNS ---- publish ----> Subscribers
                    - SQS, Lambda, Kinesis Data Firehose, emails, SMS/mobile notifications, HTTP endpoints
```

- SNS receives data from many AWS services

```
Services    -------------------------- publish -----------------------> SNS
- CloudWatch alarms, ASG notifications, CloudFormation, AWS budget
- S3 bucket [events], AWS DMS [new replic], Lambda, DynamoDb, RDS events
```

## SNS vs. SQS

- Both SNS and SQS are both managed messaging services, they are however, built on different communication models
  - Simple Notification Service vs. Simple Queue Service
  - Notification vs. Queue
    - Notification: Pub/Sub [push]
    - Queue: Message queueing [pull]

- SNS: Radio broadcast station [Push / 1-to-many]
  - instant transmission
  - many listeners [fan-out]: tune in into the frequency
  - ephemeral [no buffer]: if radio is off when the song plays, you miss it

- SQS Postal mailbox [Pull / 1-to-1]
  - durable storage: the letter stays there until you open it
  - pull-based: you need to go outside and pick it up
  - single consumer: once you your letter, it's yours. Other people can't take it
  - Pacing: if N letters arrive, you can open them little by little

```
SNS [Pub/Sub - Push]
Producer ---> [SNS Topic] ---- Push --> HTTP/Webhook
                            |- Push --> Lambda
                            |- Push --> SQS queue A
                            |- Push --> SQS queue B

SQS [Queue - Pull]
Producers --> [SQS Queue] <--- Poll [pull] -- Consumer A
                          <--- Poll [pull] -- Consumer B
```

- SNS pushes messages
  - when a publisher sends a message to an SNS topic, they are delivered across ALL SUBSCRIBED ENDPOINTS
  - if no sub exists, or if a direct HTTP endpoint id down and the retries fail, the message is lost
    - unless backed by a dead-letter queue or persistent store

- SQS holds message until pulled
  - producer places a message in the queue
  - message stays there until a consumer polls the queue to fetch, process, and delete it

# Kinesis Data Stream

- Append-only, real-time streaming data service
- Continuosly ingests and processes massive volumes of sequential data records
  - IoT telemetry, clickstreams, application metrics, financial ticker data
- Data is continous and replayable

- Kinesis has different services, depending on what you want to do with streaming data
  - data streams: collect and store
  - firehose: process and deliver
  - data analytics: analyze

- What is pull/pointer-based?
  - means consumer controls when it reads data
  - trackes where it's in the stream using a book mark, instead of deleting the record as it goes
  - for example:
    - sqs:
      - destructive consumption: as the consumer pull and processes it, it deletes the message
      - no concept of "position"/"pointer"
      - queue expands/shrinks
      - once message is consumed, it's gone
    - non-destructive offset tracking [pull/pointer-based streaming]
      - data is immutable, append-only log

```
|real-time data   |     | producers         |                 | consumers                         |
| click streams   |     | application [code]| ---> KDS ---->  | application code                  |
| IoT devices     | --->| kinesis agent     |                 | lambda                            |
| metrics and logs|                                           | data firehose                     |
                                                              | managed service for apache flink  |
```

- Retention up to 365 days
- Ability to reprocess [replay] data by consumers
- Data can't be deleted from Kinesis [until it expires]
- Data up to 10mb, however, use case is a lot of "small" read-time data
- Data ordering guarantee for data with the same "Partition ID" [shard]
- At-rest KMS encryption, in-flight HTTPS encryption
- Kinesis producer library [KPL] to write optimized producer application
- Kinesis consumer library [KCL] to write optimized consumer application

## Partition keys

- When sending a record to Kinesis data stream, you must provide a partition key
- Kinesis uses this key through a hash function to determine which specific shard the record goes to
  - if you omit/randomize the key, Kinesis will scatter records randomly across all available shard
  - set the partition key to a unique user identifier [ex: `user_id_12345`], all data records belonging to that exact user are deterministically routed to the exact same shard

## Modes

- Provisioned mode:
  - choose number of shards
  - each shard gets:
    - in: 1mb / 1k records per second
    - out: 2mb
  - scale MANUALLY to increase/decrease number of shards
  - pay per shard provisioned per hour

- On-demand mode
  - no need to provision/manage capacity
  - default capacity provisioned [4mb or 4k records/sec]
  - scales automatically based on observer throughput peak during the last 30 days
  - pay per stream per hour & data in/out per gb

### Shards

- Every shard has fixed hardware-like throughput boundaries
  - write [ingress]: 1mb/sec [or 1k records/sec] PER SHARD
  - read [egress]: 2mb/sec [or 2k records/sec] PER SHARD

## Kinesis vs. SQS vs. SNS

- SQS: A post-office letter delivery
- SNS: a megaphone
- Kinesis: cassette tape

| Feature           | SQS                                                     | SNS                                                | KDS                                                                             |
| ----------------- | ------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------- |
| Primary goal      | task execution, decoupling workers                      | broadcast alerts, push notifications               | continuous log ingestion, analytics                                             |
| Model             | queue [pull]: worker pulls, processes, deletes          | pub/sub [push]: broadcast to multiple endpoints    | streaming log [pull/pointer-based]: multiple workers read offsets in logs       |
| Consumption       | single worker processes and deletes the message         | fan out to all subs at once                        | multiple apps read the same log at their own pace                               |
| Data lifecycle    | message deleted after processing                        | ephemeral, data disappears after being sent        | immutable append-only log, retained for 1-365 days                              |
| Replayability     | no, once deleted, it's gone                             | no                                                 | yes, reset consumer points to replay historical data                            |
| Ordering          | FIFO queues only                                        | best effort, unless SNS FIFO                       | guaranteed per shard                                                            |
| Scaling mechanism | fully automatic, near-infinite throughput               | fully automatics                                   | managed via shards, provisioned or on-demand mode                               |
| Use case          | decoupling background tasks, job buffers, load leveling | fan-out notifications, alerts, webhooks, broadcast | continuous high-throughput data pipelines, log aggregation, real-time analytics |

- Kinesis should be selected when your workload requires continuous, ordered data streaming rather than task processing or notifications
- Select Kinesis when...

1. You need to replay historical data
   - Why not SQS/SNS: they delete messages once processed

2. Multiple applications must consume the exact same stream at different speeds
   - Why not SQS/SNS: SNS + SQS Fan-out can replicate messages across multiple queues
     - however, at massive scales [millions of events per second], duplicating individual messages into 4 queues
       - becomes cost-prohibitive
       - introduces management overhead

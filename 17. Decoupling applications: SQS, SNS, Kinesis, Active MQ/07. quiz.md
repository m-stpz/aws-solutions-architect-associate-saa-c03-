# Quiz: SQS, SNS, Kinesis, Data Firehose, MQ

1. You have an e-commerce website and you are preparing for Black Friday which is the biggest sale of the year. You expect that your traffic will increase by 100x. Your website already using an SQS Standard Queue, and you're running a fleet of EC2 instances in an Auto Scaling Group to consume SQS messages. What should you do to prepare your SQS Queue?

- Do nothing, SQS scales automatically
  - SQS offers nearly unlimited throughput [API calls/transactions per second] out of the box
  - Unlike provisioned services, there's no need of provisioning/reserving capacity for SQS queue
  - SQS doesn't have ASG [auto-scaling group]
    - ASG applies only to compute resources: EC2, EC2 tasks, DynamoDB capacity
  - SQS is inherently serverless and elastic
  - there's no slider, setting, API param to configure capacity on an SQS queue

2. You have an SQS Queue where each consumer polls 10 messages at a time and finishes processing them in 1 minute. After a while, you noticed that the same SQS messages are received by different consumers resulting in your messages being processed more than once. What should you do to resolve this issue?

- Increase the visibility timeout
  - visibility timeout: prevents other workers of seeing a message that is being processed
  - by increasing it, we:
    - give it more time to the consumer to process the message
    - prevent duplicate message reading

4. You have 3 different applications that you'd like to send them the same message. All 3 applications are using SQS. What is the best approach would you choose?

- SNS + SQS Fan out pattenr
  - this is a common pattern where only one message is sent to SNS and then "fan-out" to multiple SQS queues
  - this approach allows: decoupling, no data loss, ability to add new SQS queues easily

5. You have a Kinesis data stream with 6 shards provisioned. This data stream usually receiving 5 MB/s of data and sending out 8 MB/s. Occasionally, your traffic spikes up to 2x and you get a ProvisionedThroughputExceeded exception. What should you do to resolve the issue?

- Add more shards
  - Kinesis data streams in provisioned mode is governed strictly by hard limits per shard
    - per shard:
      - write 1mb/sec or 1k records/sec
      - read 2mb/sec or 5 transactions/sec
  - this scenario
    - 6 shards
      - write: 6 shards x 1mb/s = 6mb/s
      - read: 6 shards x 2mb/s = 12mb/s
    - regular hours
      - 5mb/s = below the 6mb/s limit
      - 8mb/s = below the 12mb/s limit
    - 2x spike
      - 5mb/s `*` 2 = 10mb/s
      - 8mb/s `*` 2 = 16mb/s
      - to support this traffic, we'd need at least 10 shards

- why not
  - enable kinesis replication
    - kinesis is already sync replicated across 3 AZs for durability
    - however, high availability doesn't mean more throughput
  - use SQS as a buffer to Kinesis
    - this is an anti-pattern
    - kinesis is itself a high-throughput ingestion buffer
    - placing SQS in front of kinesis:
      - adds sub-second streaming latency
      - destroys custom partition-key ordering
      - adds cost and architectural complexity

6. You have a website where you want to analyze clickstream data such as the sequence of clicks a user makes, the amount of time a user spends, and where the navigation begins and how it ends. You decided to use Amazon Kinesis, so you have configured the website to send these clickstream data all the way to a Kinesis data stream. While you checking the data sent to your Kinesis data stream, you found that the users' data is not ordered and the data for one individual user is spread across many shards. How would you fix this problem?

- For each record sent to Kinesis, add a partition key that represents the identity of the user
  - partition keys
    - they shouldn't be random. They should be unique, but stable
    - with stable partition keys, data related to the same user lives within the shard
    - when you use the identity of each user as the partition key, this ensures the data for each user is sent to the same shard

7. You are running an application that produces a large amount of real-time data that you want to load into S3 and Redshift. Also, these data need to be transformed before being delivered to their destination. What is the best architecture would you choose?

- Kinesis data stream + kinesis data firehose
  - Perfect combo for loading data near real-time data into s3 and redshift
  - Kinesis data firehose supports custom data transformations using aws lambda

- Why?
  - "large amount of real-time data" -> kinesis data streams
    - large volume of real-time data
    - kinesis data stream is purpose-built for massive, continuous, multi-gigabyte data streams
  - "transformed before being delivered" -> firehose + lambda
    - kinesis data firehose has built-in integration with AWS lambda
    - as data flows through firehose, it batches and invokes lambda functions to clean, filter, reformat, or convert data
  - "load into s3 and redshift"
    - s3 and redshift are native destination targets in firehose

- Why not SQS + lamdba?
  - SQS is designed for discrete, individual task decoupling
    - not high-volume continuous data streams

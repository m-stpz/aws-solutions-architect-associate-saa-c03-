# ECS: Elastic container service

- AWS's fully managed container orchestration platform
- Handles the lifecycle of docker containers
  - when they run
  - keeping them healthy
  - connecting them to load balancers
  - scaling them

- When running containers on ECS, choose where the compute power comes from
  - this is determined by launch type

1. Fargate: serverless, AWS provisions and manages the compute
2. EC2 launch type: you provision, manage, and scale your own cluster of EC2 VMs

## Mental model

- VPC/Subnets: the plot of land with plumbing and electricity
- ECS Cluster: the building itself [physical/virtual boundaries]
- Task definition: the architectural blueprint of an apartment layout
- ECS service: the building manager ensuring N apartments matching that blueprint are occupied, heated and repaired

## Core terminology

- Task definition: the blueprint [json doc]
  - defines which docker images to pull
  - required CPU/memory
  - env variables
  - networking mode and ports

- Task: running instantiation of a task definition
  - one or more containers working together

- Service: orchestrator for tasks
  - if tasks crashes, service replaces it
  - registers running tasks to ALB target groups and handles auto-scaling

- Cluster: logical grouping of tasks, services, and compute capacity

## EC2 launch type

- You manage it
- Create an ASG of standard EC2 instances and register them into a ECS cluster

```
+---------------------------------------------------------------+
|                       ECS Cluster                             |
|                                                               |
|  [ EC2 Instance 1 (t4g.xlarge) ] [ EC2 Instance 2 (t4g.xlarge)]|
|  +-----------------------------+ +---------------------------+ |
|  |       ECS Container Agent   | |     ECS Container Agent   | |
|  +-----------------------------+ +---------------------------+ |
|  | [Task A]  [Task B]  [Task C]| | [Task A]  [Task D]        | |
|  | (Docker)  (Docker)  (Docker)| | (Docker)  (Docker)        | |
|  +-----------------------------+ +---------------------------+ |
+---------------------------------------------------------------+
```

- Here we control the VM, so we have some features that serverless fargate doesn't offer
  - bin-packing and cost optimization
  - tasks placement strategies and constraints
  - hardware customization for specific needs

## Fargate launch type

- Serverless
  - we don't need to provision the infra -> no ec2 instance to manage
  - we just create task definition
- AWS runs ECS tasks for you based on the CPU/RAM you need
- To scale, just increase the number of tasks

| Dimension              | ECS with EC2 Launch type                                                                       | ECS with Fargate                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Server management      | High [os patching, AMI updates, ec2 agent updates]                                             | None [100% serverless, zero OS access]                                         |
| Pricing model          | pay for the ec2 instances 24/7 [whether full or empty]                                         | Pay for vCPU/RAM used                                                          |
| GPU/machine learning   | supported (g4, g5, p4 instances)                                                               | Not supported for GPU-heavy acceleration                                       |
| Cold start             | fast (5-15s) if instances have free capacity and cached images                                 | slower (30-60s+), must provision microVM and pull image                        |
| Task placement control | Granular                                                                                       | Managed by AWS                                                                 |
| Best used for          | Large-scale production clusters with predictable base loads, GPU ML workloads, custom OS needs | Standard web APIs, microservices, background jobs, unpredictable spiky traffic |

### EC2 Instance Profile vs. ECS Task roel

- EC2 Instance profile [VM level]: EC2 can talk with ECS
  - used by: underlying ec2 vm host
  - scope: applies globally to the entire ec2 server
  - purpose: allows ec2 to communicate with ECS control panel

- ECS task role: logic can interact with AWS
  - used by: container application code running inside the task
  - scope: specific to task definition
  - purpose: allows application business logic to interact with AWS

## Load Balancers Integrations

- ALB: supported and works for most use cases
- NLB: recommended for high throughput / performance use cases
  - also pairs with private link
- CLB: supported, but not recommended
  - no advanced features
  - no fargate

## EC2 Data Volumes [Persistent Data]

- Allows us to have persistent/shared data in ECS

1. EFS: Shared multi-task storage
   - Both ec2 and fargate can use it
     - Fargate + EFS: fully serverless, scales automatically to PB
   - mounts EFS file system onto ECS tasks
   - tasks running in any AZ will share the same data in the EFS file system
   - use case: persistent multi-AZ shared storage for containers

```
ECS Cluster
    | ec2 instance |     | fargate      |
    | [container]  |     | [container]  | // each container mounts the EFS
    | [container]  |     | [container]  |
--------------
        |
    Amazon EFS
    [file system]
```

2. S3 files: mount s3 file systems onto ECS tasks
   - s3 bucket exposed as file system
   - works for fargate and eCS managed instances
     - ECS launch type IS NOT supported
   - changes sync automatically to s3 bucket
   - use case: containers needing shared file access to data existing in s3

## Hands on

1. Create the cluster: defining the boundary and capacity

- name, infra
- you established the boundaries, but no application code is yet running

2. Navigate inside cluster

- services/tasks/infra/metrics

3. Add and create the service: attaches an application workload to that compute pool

### Hands on - ECS Cluster

- You create the ECS cluster
  - name
  - infra: fargate only, fargate and managed instances, fargate and self-managed instances [old]
  - create instance profile
  - create infrastructure role
  - instance selection
    - ecs default: recommended -> ECS creates based upon task definition and service requirements
    - custom: advanced -> specify instance attributes or exact instance types
      - VCPU
      - Memory
- It'll create a ASG, depending the infra
- Depending on the ASG parameters [min/desired/max], it will spin instances and register it on the cluster

- Step 0: Container image
  - your code is containerized
  - build your docker image locally: `docker build -t my-app:latest`
  - auth docker with aws and push image to ECR

```
docker tag my-app:latest <account_id>.dkr.ecr.<region>.amazonaws.com/my-app:v1
docker push <account_id>.dkr.ecr.<region>.amazonaws.com/my-app:v1
```

- Step 1: Create the task definition [bluepint]
  - ECS / Task definition / create new task definition
  - Infra setting
    - launch type: fargate/ec2
    - define overall task sizing
    - assign the `Task Execution Role`: allows ECS to pull the ECR image and push logs
    - assign the `Task role`: grants app permissions to s3, dynamodb, etc
  - Container config
    - container name
    - paste the ECR image URI from step 0
    - define container port mappings
    - Set env vairables / link secret paths from SSM param store / secrets manager
    - enable CloudWatch logging
  - click Create to save Revision 1 (ex: `my-app:1`)

- Step 2: Create the ECS cluster [compute boundary]
  - ECS / Clusters / Create Cluster
  - name cluster
  - compute infra
    - fargate: no servers to provision, managed capacity enabled by default
    - ec2: select EC2 ASG, choose AMI [Amazon ECS-Optimized Linux], instance types, key pairs and desired instance count
  - select VPC and public/private subnets
  - create

- Step 3: Create the ECS Service [controller and lifecycle manager]
  - ECS / Clusters / <my-cluster> / Services tab / Create
  - Env and compute: choose compute strategy [fargete or EC2 cluster pool]
  - Deploy config
    - application type: Service [long-running apps like web servers or background workers]
    - family: select `Task definition` from Step 1
    - revision: select `Latest` or specific revision
    - name
    - desidered tasks: number of concurrent copies to keep alive
  - Networking and security
    - choose VPC and subnets where tasks should be placed [normally private subnets]
    - attach a security group that allows inbound traffic on your container port ONLY from your LB
  - Load balacing [optional for web APIs, skip for workers]
    - select ALB
    - choose ALB listener
    - point to/create a Target Group that forwards traffic to the container port
  - Auto scaling:
    - config minumum and maximum task counts
    - choose metric policy
      - ex: Target tracking: keep average ECS CPU usage at 70%

> As a rule of thumb, a Task = Running instance of the container

## ECS Auto Scaling

- Automatically increase/decrease the desired number of ECS tasks
- ECS auto scaling group uses AWS Application Auto Scaling
  - ECS service average CPU utilization
  - ECS service average Memory utilization - scale based on RAM
  - ALB request count per target - metric coming from the ALB

- Scaling based on:
  - Target tracking: target value for a specific CloudWatch metric
    - Target = CloudWatch metric
  - Step scaling: specified CloudWatch alarm
    - Step = CloudWatch alarm
  - Scheduled scaling: specified date/time [predictable changes]

- ECS service auto scaling (task level) != EC2 auto scaling (ec2 instance level)
- Fargate auto scaling is much easier to setup, since it's serverless

### EC2 Launch Type: Auto Scaling EC2 Instances

- Adds more underlying EC2 instances to our ECS service scaling

- Auto scaling group scaling [works, but older]
  - scales ASG based on CPU utilization
  - add EC2 instances over time

- ECS cluster capacity provider [modern, suggested]
  - modern and recommended approach
  - used to automatically provision and scale the infra for your ECS tasks
  - capacity provider paired with ASG
  - Add EC2 instances when you're missing capacity [RAM/CPU...]

## ECS Fargate vs. Lambda

3 Architectural drivers for this decision

- execution duration/state
- traffic patterns/cost profile
- control over runtime environment

| Dimension                 | Lambda                                                             | ECS / Fargate                                                                  |
| ------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| Execution model           | Ephemeral, event-triggered function                                | Long-running, persistent process                                               |
| Execution limit           | Max 15min. for standard invocations                                | Unlimited                                                                      |
| Startup latency           | Sub-second, but subject to cold starts                             | 30-60s on Fargate; 5-15s on warm EC2 instances                                 |
| Concurrency / scaling     | Near-instant horizontal scaling [thousands of workers in seconds]  | Step/target-tracking scaling [1-3 min to scale tasks]                          |
| Network protocols         | HTTP req/res via API gateway/ALB, gRPC limited                     | Full TCP/UDP, persistent WebSockets, gRPC, custom ports                        |
| State and in-memory cache | Stateless; memory wiped when container freezes/terminates          | State in-memory pools, shared threads, local cache                             |
| Cost dynamics             | Cheaper for intermittent, bursty, or low traffic                   | Cheaper for predictable, sustained high throughput                             |
| Local dev                 | Emulation tools (`sam local`, LocalStack), non-identical           | Bit-for-bit parity via native `docker compose`                                 |
| Use case                  | workload is event-driven, rapid scale-out, standard APIs with HTTP | Long-running execution, persisten connections [WebSockets, long polling, gRPC] |

- Reacts to event, takes under 15 min and traffic fluates? Lambda
- Needs shared in-memory state/pools, longer execution, or persistent connection? ECS

## ECS vs EC2

- Even with ECS and modern container orchestration, some teams still intentionally deploy architectures using raw ECS instancs in an ASG behind an ALB

1. Legacy monoliths

- hardcoded filesystem paths
- system-level registry keys
- refactoring or wrappig them into docker isn't doable
  - commercially unsopported
  - technically undoable
  - not worth the engineering cost

2. Deep kernel customizations, drivers and low-level tuning

- if application requires custom linux kernel modules, specialized filesystem drivers
- High-performance computing [HPC]/algorithimic trading workloads achieve better latency without docker network virtualization layers

3. Avoiding multi-layered autoscaling complexity

- With raw ECS + ASG, there's only one scaling layer
- With ECS on ECS, there are 2 scaling layers
  - ECS service autoscaling: to scale tasks based on CPU/RAM/Queue
  - EC2 capacity providers: to scale the underlying VM fleet to fit those tasks

4. Some licesing requirements

## ECS - Solutions Architectures

- Fundamentally, the macro-architectural patterns remain identical whether you use EC2 or ECS
- Diffrence is on the operational mechanics and deployment topology

1. Public web API pattern [ALB + ECS service]

- Standard design for REST APIs, GraphQL servers and public web applications

```
client ---> ALB [public subnet] -------------------> ECS Service [private subnet] -----> Aurora/DynamoDB/ElastiCache
      SSL termination, Path/Host routing            task 1 container on 8080
                                                    task 2 container on 8080
                                                    task 3 container on 8080
```

2. Microservices with internal service mesh [ECS service connect]

- Used when decomposing systems into multiple decoupled services that need to talk to each other without exposing endpoints publicly

```
frontend ECS service --------------> ECS service connect sidecar [proxy] ---------> Orders backend ECS service tasks
    calls http://orders.production:8080                           mTLS / internal discovery
```

3. ECS tasks invoked by Event Bridge

- standard architectural pattern for scheduled cron jobs (ex: nighly batch reports) event-driven batch jobs
  - ex: triggering a 45-min video rendering task whenever a new video is uploaded to s3

```
Event Trigger (e.g., Cron Schedule OR S3:ObjectCreated via EventBridge)
                            │
                            ▼
           [ Amazon EventBridge Rule / Scheduler ]
                            │
              (Assumes EventBridge Target IAM Role)
              (Calls ecs:RunTask with overrides)
                            ▼
           [ Amazon ECS Cluster (Fargate / EC2) ]
                            │
                    [ ECS Task Boots ]
               (Reads injected event payload)
               (Executes long-running script)
                            │
                            ▼
                   [ Task Terminates ]
```

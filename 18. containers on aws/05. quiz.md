# Quiz - Containers on AWS

1. You have multiple Docker-based applications hosted on-premises that you want to migrate to AWS. You don't want to provision or manage any infrastructure; you just want to run your containers on AWS. Which AWS service should you choose?

- AWS Fargate on AWS
  - Allow you to run containers on AWS without managing the servers
  - Just a note:
    - Fargete carries a 20% to 50% premium over equivalent on-demand ec2 instances
    - however, if the bill will be higher or lower on Fargate depends on utilization curve
    - Raw prices, however, tell only half of the story, while EC2 charges for the entiry VM, fargate charges for the container resource request
      - there's no wasted compute with fargate

> Rule of thumb: start on Fargate by default for simplicity and zero maintenance. If the bill gets too large to justify engineering time, then you switch to ECS on EC2

2. Amazon Elastic Container Service (ECS) has two Launch Types: .................. and ..................

- EC2 Launch type / Fargate

3. You have an application hosted on an ECS Cluster (EC2 Launch Type) where you want your ECS tasks to upload files to an S3 bucket. Which IAM Role for your ECS Tasks should you modify?

- Wrong:
  - EC2 Instance profile
    - EC2 Instance profile is the IAM role used by the ECS agent on the ECS instance to execute ECS-specific actions
      [ex: pulling docker images from ECR and storing the container logs into CloudWatch logs]

- Correct:
  - EC2 Task role
    - IAM role used by the ECS task itself
    - Use when your container wants to call other AWS services like S3, SQS, etc

4. You're planning to migrate a WordPress website running on Docker containers from on-premises to AWS. You have decided to run the application in an ECS Cluster, but you want your docker containers to access the same WordPress website content such as website files, images, videos, etc. What do you recommend to achieve this?

- Mount EFS volume
  - EFS volumes can be shared by different ec2 instances and different ECS tasks
  - can be used as a persistent multi-az shared storage for your containers

5. You are deploying an application on an ECS Cluster made of EC2 instances. Currently, the cluster is hosting one application that is issuing API calls to DynamoDB successfully. Upon adding a second application, which issues API calls to S3, you are getting authorization issues. What should you do to resolve the problem and ensure proper security?

- Create IAM task role for the new application
  - why?
    - granular task isolation
    - each application in ECS has its own Task Definition
    - application 1 has its own task role allowing API calls to dynamo db
    - when you introduce app 2, it should NOT inherit/share permissions it doesn't need
      - creating dedicated IAM task role for app 2 with permissions scoped to s3 solves auth failure without exposing dynamodb to app 2 or s3 to app 1

- Applicaiton 1 [A1] should have access to dynamo db
  - thus A1 has a IAM task role for dynamodb, but not for s3
- A2 should have access to s3
  - thus A2 has a IAM task role for s3, but not for dynamodb

Why not?

- Edit the EC3 instance role to add permissions to s3
  - ec2 instance role attaches directly to host VM
  - if you add s3 permissions there, EVERY CONTAINER running on that ec2 instance has access to s3
    - thus, you break security isolation
    - AWS best practice: application permissions belong on the Task Role, NOT on the host VM
- Enable the fargate mode
  - changes compute model, not the IAM permission errors
- Edit s3 bucket policy to allow the ECS task
  - s3 bucket policies grant access to an IAM principal

6. You are migrating your on-premises Docker-based applications to Amazon ECS. You were using Docker Hub Container Image Library as your container image repository. Which is an alternative AWS service which is fully integrated with Amazon ECS?

- Elastic Container Registry [ECR]
  - fully managed container registry
  - easy to store, manage, and deploy container images

7. Amazon EKS supports the following node types, EXCEPT ………………..

- AWS Lambda
  - Lambda is an event-driven serverless functoin service, not a k8s compute node
  - it can't join a k8 cluster

- It accepts:
  - Managed node groups: pre-config ec2 ASG
    - aws automates node provisioning, updates, patching and node draining
  - Self-managed node groups: standard ec2 instances
    - launched manually or via custom ASG
    - uses custom AMIs and bootstrapping scripts
    - you manage patches and OS lifecycle
  - AWS fargate
    - serverless compute for EKS

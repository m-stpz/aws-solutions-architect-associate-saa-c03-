# Docker

- Docker is a software development platform to DEPLOY apps
- Apps are packaged in CONTAINERS that can be run on any OS
- Apps run the same, regardless of where they're run
  - any machine
  - no compatibility issues
  - predictable behavior
  - less work
  - easier to maintain and deploy
  - works with any language, OS, tech

- Use cases:
  - microservices architecture
  - lift-and-ship apps from on-prem to cloud

- Docker images are stored in docker repositories
  - docker hub
    - public repo
    - find base images for many tech or OS
  - Amazon ECR [amazon elastic container registry]
    - private repo
    - public repo [Amazon ECR public gallery]

## Getting started with docker

1. Write dockerfile
2. Build the docker image
3. Push the image to a docker repo [dockerhub/ecr]
4. Pull the image from the docker repo
5. Run the docker image

## Docker containers on AWS

  - amazon's own serverless container platform

## Docker vs. VM

- VM virtualizes the hardware
  - emulates the entire hardware components [CPU, memory, storage]
- Docker virtualizes the OS
  - virtualizes the user spaces, shares the host OS kernel directly

| Feature              | Docker containers                                                        | Virtual machines (VMs)                                                    |
| -------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| Virtualization layer | OS                                                                       | Hardware                                                                  |
| Startup time         | ms to seconds                                                            | minutes: must boot a complete OS,run system/init, and mount drivers       |
| Resource overhead    | Very lightweight: minimal CPU/memory overhead                            | Heavy. Requires dedicated RAM/CPU allocation and gb of disk spaces per OS |
| Use cases            | microservices architecture, CI/CD pipelines, testing envs, local dev env | legacy and monolithic apps., multi-os workloads, untrusted code execution |

### EC2 or Docker?

#### Docker [Containers]

default choice for modern applications

- use it for:
  - web APIs and full-stack services

1.  fast horizontal scaling

- if traffic spikes, spinning up a new container takes seconds
  - booting a full ec2 instance from an AMI and running user data scripts takes MINUTES

2. docker + aws fargate provides ZERO SERVER MANAGEMENT

- define CPU/memory per task and AWS handles provisioning the underlying compute

3. Microservices and multi-tenant density
   - instead of paying for 5 different ec2 instances to run 5 separate microservies [wasting idle RAM/CPU], run all 5 containers o na single clustered compute environment

4. CI/CD consistency
   - what runs on your local machine is bit-for-bit identical to prod

#### EC2 [VMS]

used when the application requirements conflict with container lifecycle or need BARE-METAL OS access

1. Stateful monoliths and legacy apps
   - applications that expect permanent filesystem, fixed system-level config or direct host OS management
   - standard monolithic wordpress, legacy CMSs, enterprise COTS software

2. Deep OS / kernel customization
   - application needs specific linux kernel modules, custom network device drivers, or specific system-level config

## Layers

1. Artifact layer
2. Contract layer
3. Orchestration layer
4. Compute layer

### 1. Artifact layer [where code lives]: docker image | application code + runtime

- amazon ECR
- where code lives

1. write app code
2. run `docker build`

- packages app code, language runtime, system libs, deps into a docker image

3. push the image to a container registry (dockerhub/ECR)

> At this stage the image is static storage. It has no CPU/RAM and doesn't execute anywhere

### 2. Contract layer [task definition]: ECS task definition | CPU/RAM sizing, ports, env vars

- Before ECS can run the container, we must define the resource boundary -> task definition [declarative JSON blueprint]
- Bridge between container + compute environment

> Whenever this container runs, allocate <vCPU> and <RAM>

### 3. Orchestration [instantiation]: ECS service / cluster | health checks, scaling, scheduling

- Task definition is just a blueprint
- To make it run, ECS service instantiates it 1 or N running tasks
- ECS scheduler decides
  - how many tasks must stay alive
  - host to register them with ALB target group
  - where to find compute for them

### 4. Compute layer [execution]: EC2 launch type / fargate | physical/virtual hardware

- Here is when EC2 launch type vs. Fargate comes to play
- The container processes must execute on real CPU and consume physical RAM

- EC2 launch type: you manage the compute
- Fargate: serverless

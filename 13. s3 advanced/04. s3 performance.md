# S3 Performance

## Baseline performance

- S3 is by default incredibly scalable
- It automatically scales to high request rates
  - latency 100-200ms
- Application can achieve `_____` requests per second per prefix in a bucket
  - 3,5k PUT/COPY/POST/DELETE [mutations]
  - 5,5k GET/HEAD [query]
- No limits to the number of prefixes in a bucket
- What is a prefix?
  - the path between the bucket/ ... to the / file

```
      | -- prefix ---|
bucket/folder/1/sub1/file
```

| object path              | prefix         |
| ------------------------ | -------------- |
| bucket/folder1/sub1/file | /folder1/sub1/ |
| bucket/folder1/sub2/file | /folder1/sub2/ |
| bucket/1/file            | /1/            |
| bucket/2/files           | /2/            |

- If we spread reads across all prefixes evenly, we can get 22k requests per second for GET/HEAD

## Performance

### 1. Multi-part upload

- recommended for files > 100MB,
- must use for files > 5gb
- can help parallelize uploads

```
        parallel uploads / chunk
         / part 1  \
big file -- part 2 -- amazon s3
         \ part 3 /
                s3 assembles it
```

- Basically, it breaks the file into smaller chunks
  - these chunks are uploaded concurrently or even out of order over the network
  - then s3 assembles it into a coherent object

Under the hood:

1. initiation
   - send a request specifying:
     - destination bucket
     - object key
     - optional object metadata [tags, encryption headers like KMS keys, storage class]
     - s3 generates and returns an `UploadId`
       - a string that allows it to track the operation
2. uploading parts
   - client slices the source binary into chunks
   - each chunk is dispatched with:
     - `UploadId`
     - `PartNumber` ranging from 1 to 10k
   - parts can be sent in parallel across multiple worker threads/network sockets
   - parts don't need to arrive in sequential order
   - if a chunk fails, only that single chunk needs to be retried, not the entire file
   - for each accepted part, S3 writes the byte range to storage and replies with an HTTP header container an `ETag`
3. completion
   - client sends a final manifest to S3 containing the `UploadId` and an XML/JSON payload with all part numbers and their returned `ETag` hashes sorted
   - s3 concatenates the chunks in the specified order, register the final object metadata, and writes the object entry to the bucket index

```xml
<CompleteMultipartUpload>
  <Part><PartNumber>1</PartNumber><ETag>"hash1"</ETag></Part>
  <Part><PartNumber>2</PartNumber><ETag>"hash2"</ETag></Part>
</CompleteMultipartUpload>
```

### 2. Transfer acceleration

- increase transfer speed by transferring file to an AWS edge location, which will then forward the data [through private aws network] to the s3 bucket in the target region
- Compatible with multi-part upload

```
            fast                fast
        [public wwww]       [private aws]
file in USA ---> edge location ---> s3 bucket
                [usa]               [australia]
```

### 3. Byte-range fetches

- Parallize GETs by requesting specific byte ranges
- Better resilience in case of failures
- Can speed up downloads

```
[---------- file in s3 ---------]
[--part1-][--part2-]...[--partN-]
    - requests in parallel
```

- Can also be used to retrive a PARTIAL data, ex: head of a file

# Lifecycle rules

- We can transition objects between storage classes

- You don't need frequent access?
  - move them to standard IA [infrequent access]
- You don't need fast access?
  - move them to glacier or glacier deep archive

- This moving can be automated through lifecycle rules

## Rules

- Transition actions: config objs to transition to another storage class
  - ex:
    - move objects to standard IA class N [60] days after creation
    - move to glacier after N days [6 months] after creation
- Expiration actions: config objs to expire/delete after some time
  - access log files can be set to delete after 365 days
  - can be used to delete old versions of files [if versioning is enabled]
  - can be used to delete incomplete multi-part downloads
    - ex: if it's 2 weeks old, it should have been completed by now. get rid of it

- Rules can be created for specific:
  - prefixes: `s3://mybucket/mp3/*`
  - object tag: `department: finance`

## Scenarios

1. Your application on EC2 creates images thumbnails after profile photos are uploaded to Amazon S3. These thumbnails can be easily recreated, and only need to be kept for 60 days. The source images should be able to be immediately retrieved for these 60 days, and afterwards, the user can wait up to 6 hours. How would you design this?

- requirements
  - thumbnails
    - can be recreated
    - only kept for 60 days -> meaning, we can delete them
  - source image
    - immediately retrived for 60 days
    - after, use can wait up to 6 hours -> glacier

- thumbnails
  - initially one-zone IA -> after 60 days -> expire them
- source image
  - initially standard -> after 60 days -> glacier

- S3 source images can be on standard, with a lifecycle config to transition them to glacier after 60 days
- S3 thumbnails can be on one-zone IA, with a lifecycle config to expire/delete them after 60 days

2. A rule in your company states that you should be able to recover your deleted S3 objects immediately for 30 days, although this may happen rarely. After this time, and for up to 365 days, deleted objects should be recoverable within 48 hours. How would you design this?

- requirements
  - recover deleted s3 objects immediately for 30 days -> needs versioning [deleted objects are hidden by a "delete marker"]
    - happens rarely
  - after 30 days and for 365 days, deleted objects should be recoverable within 48 hours -> glacier

- we need
  - versioning
    - this way, the objects have a "delete marker" and can be recovered
  - transition "noncurrent versions" of the object to standard IA [for 30 days]
  - transition afterwards the "noncurrent versions" to glacier deep archive [after 30 days -> for 365 days]

## Storage class analysis

- AWS offers analytics into your S3 bucket
  - it provides a .csv report on it
  - report is updated daily
  - 24-48h to start seeing data analysis
- They help to transition objects to the right storage class
- Through it, it'll give you recommendations for standard and standard IA
  - does NOT work for one-zone IA or glacier

> Very helpful for understanding better lifecycle rules and how you can optimize your s3 storage

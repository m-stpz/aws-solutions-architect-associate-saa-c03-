# IAM - Identity and Access Management

- Global control plan that governs `______` across AWS account
  - authentication: who you are
  - authorization: what you can do
- Virtually every action within AWS is evaluated by IAM before executing

## 4 Core IAM identities [principals]

- Root user
  - single initial identity on account creation
  - unrestricted superuser acceess
  - account-level administrative tasks only
    - closing account, changing supporti plans, modifying root email
- IAM user
  - a long-term identity representing a single human or legacy service
  - individual devs
    - AWS recommends IAM identity center / SSO over IAM users for human workforce access
- IAM group
  - logical collection of IAM users
  - assigns shared permissions
  - groups can't be nested within groups
- IAM role
  - A temp identity with permissions that aren't tied to a person
  - EC2 instances, lambda functino, ECS tasks, cross-account access, and federated SSO users

## IAM Policies - How permissions are defined

- Identities start with zero permissions by default
- You grant or restrict access by attaching IAM policies
  - JSON document compose of 1 or more `Statement` Blocks

- Effect: allow/deny
- Action: API operations
- Resource: exact amazon resource name [ARN] the action applies to
- Condition: extra logic

- Identity-based vs. resource-based policies
  - Identity-based: attached to IAM user, group, or role
    - what can this identity do?
  - Resource-based: attached to AWS resource
    - who's allowed to access this resource?

## IAM policy evaluation logic

- All policies are evaluated through a hierarchy

1. Default deny: if no policy allows an action, it's blocked
2. Explicit deny overrides everything: if a policy has "deny" matching the request, access is denied
   - even if other related policies say "allow"
3. Explicit allow grants access: if there's no explicit deny and at least one "allow", then request is allowed

Explicit deny > Explicit allow > Implicit deny [default]

## Best practices

1. Principle of least privilege: grant only exact permissions to perform specific task
   - avoid generalizations and wildcards
2. IAM roles over long-term access keys: never hardcode IAM user access keys inside application code, docker images or EC2 instances
   - attach IAM instance profile / execution role so AWS STS delivers rotating temp credentials

## Advanced intro

1.  cross-account access and role chaining

- exams love testing the difference between:
  - assuming a role
  - using a resource-based policy across accounts

2. AWS orgs and service control policies [SCPs]

- SCPs are the account-level cousin of permission boundaries
  - what they don't affect
    - the management [payer] account: SCPs never restrict the management account, even if attached to the root OU
    - AWS service-linked roles

3. attribute-based access control [ABAC]

- instead of updating policies every time a new project or dev is added [RBAC], ABAC scales permissions using tags

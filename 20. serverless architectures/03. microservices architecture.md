# Microservices architecture

- We want to switch to microservices
- Many services interact with each other directly using REST API
- Each architecture for each microservice may vary in form/shape
- Microservices allow leaner and more decoupled development lifecycle

- Application is structured as a collection of small, autonomous, and independently deployable services
  - organized around business domains

```
               ┌───────────────────────┐
               │      API Gateway      │
               └───────────┬───────────┘
                           │
       ┌───────────────────┼───────────────────┐
       ▼                   ▼                   ▼
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│ User Service │    │ Order Service│    │Payment Service│
│ (Node.js)    │    │ (Go)         │    │ (Java)       │
├──────────────┤    ├──────────────┤    ├──────────────┤
│ PostgreSQL   │    │ DynamoDB     │    │ Aurora MySQL │
└──────────────┘    └──────────────┘    └──────────────┘
```

- Sync patterns: API gateways, load balancers
- Async patterns: SQS, Kinesis, SNS, Lambda triggers

## Polyglot architecture and different stacks

- Each microservice exposes a standardized network interface, then the internal implementation is encapsulated
  - one service can run nodejs + postgresql: rapid json-heavy CRUD
  - another can run python + redis: machine learning/data scoring
  - high-throughput ingest pipeline in go or rust + dynamodb
- Teams pick best runtime, persistence model, framework for the specific use case, instead of relying on a single company-wide framework

## Leaner, decoupled development and deployment cycles

- Autonomous teams
- Isolated blast radius
- Independent scalability
- Zero-downtime CD

## Db-per-service pattern

The defining technical constraint of true microservices is that services MUST NEVER SHARE a DB

- services access another domain's data strictly through public API contracts or event streams

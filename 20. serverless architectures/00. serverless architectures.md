# Serverless architectures

- Serverless architecture has grown from simple "API Gateway + lambda" setups into:
  - specialized, event-driven topologies
  - handle scale, decouple services and avoid common serverless anti-patterns

## 1. Decoupled async processing [Storage-first / Queue-based load leveling]

Instead of passing heavy req sync from API endpoint to compute, requests are buffered into a queue/event stream

```
                                                                batch/retry
Client --- POST ---> API Gateway ----- direct integration ---> SQS ----> Lambda ---> Dynamo db
                                                                                        | failed items?
                                                                                        DLQ
```

- Core mechanics
  - Uses API gateway native AWS service proxy to drop messages straight into SQS without invoking lambda just to act as a pass-through
  - Lambda polls SQS via Event Source Mapping [ESM] in controlled batches with config conc limits
  - Failed messages go to DLQ after N retry attempts

- Why it's used
  - flattens spiky traffic
  - protects downstream db from connection overload
  - guarantees messages durability even if compute/db fail

- Use cases
  - order placement
  - backgroud report generation
  - transactional notifications [SMS/email]

## 2. Event-driven choreography [Pub/sub & event bus]

Instead of making direct sync HTTP calls to each other, services communicate async by emitting events when domain state changes

```
                                                        / Rule: EU orders ---> Invoice service
order service ---> emits "OrderPlaced" ---> EventBridge --- Rule: All -------> Inventory service
                                                        \ Rule: Fraud check -> Fraud Lambda / Step func
```

- Core mechanics
  - uses EventBridge or SNS as a centralized routing hub
  - producers publish domain events without knowing who consumes them
  - consumers filter out irrelevant messages/events

- Why it's used
  - eliminates point-to-point coupling between services
  - new features/consumers can be added with no change to existing services
  - isolates blast radius

- Use cases
  - e-commerce fulfillment
  - cross-domain workflows in microservice arhictecutre
  - 3rd party saas event ingestion [ex: stripe, shopify]

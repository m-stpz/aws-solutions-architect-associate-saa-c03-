- Blogs are rarely written, most often read: read ratio > write ratio
  - cache reads with DAX?
  - CloudFront for CDN
- Some of the website is purely static files, rest is dynamic REST API
  - static files: s3
  - dynamic REST API: API gateway + lambda
- caching must be implemented where possible
- new subs receive welcoming email
  - SNS
  - or dynamodb streams -> lambda -> SNS
  - ways to achieve this?
- uploaded photo to the blogs have a thumbnail
  - s3 for the image
    - s3 upload
    - add metadata to dynamo
    - dynamo streams triggers lambda and resizes it and writes to s3 again?
  - how can we achieve post-processing

## Questions

- Caching
  - Do we need DAX?
    - CloudFront is more than enough
    - DAX: fixed cost [$100-$150/month] + VPC plumbing
  - Cache invalidation
    - how should we update the cache on blog post delete/update?
      - TTL-based or on-demand?
      - TTL-based with a 2h time-window? -> bad, instead use event-based targeted invalidation
      - event-based cache invalidation
        - updateBlog/deleteBlog we invalidate /blog/<id> cache
          - updates on the db
          - invalidates the cache

- email notification
  - SNS: unformatted, simple alerts
  - SES: default for welcome emails, branding
  - ingestion path: sync API or dynamodb stream?
    - async flow is fine here

- image uploads + thumbnail generation[post-processing on s3 event]
  - upload credentials
    - API gateway?
      - 10mb payload limit + compute price
    - Cognito identity pool?
      - it'd be fine to provide the user with auth to upload to his portion of the bucket
      - not good for this use case, we need more granular control and simpler API, pre-signed is better
    - S3 pre-signed URL
      - lambda returns a pre-signed url with specific permissions
  - trigger mechanism
    - s3 `ObjectCreated` event to lambda should be fine
    - if we need more scale or deal with higher/uneven traffic, we can add SQS

## Main aspects

- Static content being distributed using CloudFront + s3
- REST API with API Gateway + Lambda
- Create user: dynamodb streams + lambda + SES
- Upload image: cognito for auth + s3 pre-signed url
  - no bytes passing through backend
  - either 2 s3 buckets or isolated prefixes -> avoids lambda loops
  - trigger mechanism for post processing
    - s3:ObjectCreated -> lambda -> updates entry db + adds processed result on s3
    - no need for dynamodb data stream in this case
- cache invalidation: event-based invalidation
  - updateBlog/deleteBlog

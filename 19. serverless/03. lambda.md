## Lambda Integrations

Lambda has 3 invocation models

- Sync: req/res
- Async: event-driven
- Event source mapping [polled streams/queues]

### Sync integrations: caller waits for lambda to return

- API Gateway: epxoses HTTP/REST/WebSockets APIs
  - routes client requests to lambda, waits for the response, and sends JSON back to caller
- ALB: routes HTTP traffic directly to lambda as a target group, without requiring an API gateway
- Cognito: hooks into user auth lifecycles [pre-signup, post-confirmation, token generation] to customize auth flows
- Step functions: orchestrates multi-step workflows by executing lambda tasks sequentially or in parallel, awaiting completion before branching

### Async integrations: fire-and-forget, aws manages retries

- S3: emits events on file uploads/deletion to trigger background processing
  - image resizing
  - csv ingestion
- EventBridge [CloudWatchEvents]: functions as a serverless event bug
  - triggers lambda on scheduled con rules
  - reactive events emitted from over 200 AWS services and SaaS partners
- SNS: publishes messages across multiple subs [fan-out pattern]
  - async executes lambda in parallel
- SES [Simple Email Service]: fires lambda function when inbound email arrives to parse attachments or route contents

### Event source mapping: lambda polls the source for you

- SQS: lambda automatically polls the queue, batches messages, invokes your func, and deletes processed messages upon success
- DynamoDB streams: emit item-level modification events [INSERT, MODIFY, REMOVE] that lambda reads in strict chronological order per shard to build audit trails or updates cache
- Kinesis data stream: ingests high-throughput real-time data [IoT, logs, clickstreams] where lambda reads and processes ordered shards in micro-batches
- MSK/Apache kafka: polled by lambda internal poller to consume streaming messages from kafka topics without keeping worker VMs running

## EC2 vs Lambda

- Infrastructure-as-a-service [IaaS]: EC2
- Function-as-a-service [FaaS]: Lambda

| Dimension             | EC2                                                                   | Lambda                                                                   |
| --------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Abstractions          | Full VM [OS, kernel, CPU, RAM, storage]                               | Ephemeral, stateless function handler                                    |
| Execution time        | Unlimited [runs 24/7]                                                 | 15min. max per invocation                                                |
| Scaling               | Metric-based via ASG [minutes to boot]                                | Automatic, immediate concurrency scaling [sub-second]                    |
| Billing model         | Pay per second/hour while instance is running, even if idle           | Pay per ms of compute time consumed [$0 when idle]                       |
| Maintenance           | Patch OS, install security updates, tune networking, config runtimes  | Zero server maintenance, AWS managed the underlying env and OS           |
| Network and protocols | Full TCP/UPD, raw sockets, web sockets, persistent background daemons | Req/res via HTTP [API Gateway/ALB], even triggers, or gRCP               |
| State and memory      | stateful: local disk persistence, in-memory caches, connection pools  | Stateless: execution context freezes or gets destroyed after invocations |

- EC2
  - virtual servers in the cloud
  - limited by RAM/CPU
  - continuously running
  - scaling means intervention to add/remove servers

- Lambda
  - virtual functions, no servers to manage
  - limited by time: short executions < 15min
  - run on-demand
  - scaling is automated

### When to use EC2

- Long-running processes: workloads that run for > 15min
  - continous background loops
  - complex video/data rendering
  - long-standing multi-hour processes
- Sustained, steady 24/7 traffic
  - high, predictable throughput are far cheaper per unit of compute than lambda
- Control over OS and env
  - custom kernel extensions
  - GPU config
  - low-level system daemons
  - specific OS dist
  - software licenses tied to CPU sockets/host hardware
- In-memory caching & persistent connection: applications relying on continous TCP/WebSocket connections
  - chat apps, gaming serves
  - stateful db connection pools

### When to use Lambda

- Event-driven workloads: reacting to AWS events
  - S3 file upload
  - new dynamoDB stream entry
  - SQS message arrival
- Bursty/unpredictable traffic: surges or periods with low traffic
- Lightweight APIs and micro-logic:
  - REST/HTTP endpoints
  - webhooks
  - authentication authorizers
  - cron scripts that execute in ms or seconds
- Zero infra overhead: small teams or microservices where too much infra is a hassle not a desired/needed evil

## Lambda with API Gateway or ALB?

This decision comes down to:

- cost at scale: > 10/20M requests/month? ALB is cheaper than API gateway
  - for high-throughput, sustained traffic, ALB wins
- hybrid routing: ALB allows routing traffic from monolithic to serverless incrementally

Rule of thumb

- Building external-facing API that requires `____`, then -> API Gateway
  - API keys
  - rate-limiting/throttling
  - usage plans
  - request validation
  - low/spiky traffic

- Handling high-volume sustained web traffic [10/20M+ monthly req], or `_____`, then -> ALB
  - mix of lambda with ec2/ecs microservices under one domain
  - requests that take longer than 29s?

## Lambda Limits

- Execution
  - memory allocation: 128mb - 10gb [1mb increments]
  - maximum execution time: 900s [15min]
  - env vars: 4kb
  - disk capacity in the "function container" [in /tmp]: 512mb - 10gb
  - concurrent executions: 1k [can be increased]

- Deployment
  - lambda function deployment size [compressed .zip]: 50mb
  - size of uncompressed deployment [code + deps]: 250mb
  - can use the /tmp dir to load other files at startup
  - siz env vars: 4kb

## Concurrency & Throtteling

- Concurrency limit: 1k concurrent executions
- Can set a "reserved concurrency" at the func level [=limit]
  - Each invocation over the concurrency limit will trigger a throttle
    - throttle behavior:
      - if sync invocation = return ThrottleError 429
      - if async invocation = retry automatically and then go to DLQ
- Need higher limit? support ticket

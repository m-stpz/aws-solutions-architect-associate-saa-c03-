# Serverless

- New paradigm where devs don't have to manage servers anymore
- They just deploy code
- Initially serverless was applied to functions
  - it was FaaS: function as a service
  - however, nowadays it has grown to dbs, messaging, storage, etc
  - anything that is managed and allows you not to worry about the underlying server
- Serveless doesn't mean that there are NO servers, instead you don't manage/provision them
- Devs build and run applications without `___` the underlying virtual servers/containers
  - managing
  - patching
  - maintaining

## Core operational traits

- Zero server management: you never SSH into a host, install an OS, update packages, or manage runtimes
- Automatic, Elastic scaling: capacity scales automatically based on consumption
- Pay-for-value billing: no charge for idle compute
- Built-in high availability and fault tolerance: services operate natively across multiple AZs by default

## Serverless services in AWS

- Not just compute, an ecosystem across compute, storage, messaging and orchestration

- Compute
  - AWS lambda: ephemeral functions
  - AWS fargate: containers

- Storage and db
  - s3: object store
  - dynamoDB: serverless NoSQL
  - aurora serverless: auto-scaling relational db

- Integrations and messaging
  - API gateway: Rest/HTTP/WebSocket endpoints
  - EventBridge: serverless event bus
  - SNS: pub/sub push
  - SQS: message queuing

- State and orchestration
  - AWS step functions: visual state machines and workflow orchestration

## Common serverless architectures

### 1. The sync 3-tier web api / API pattern

baseline pattern for SPAs, mobile aps, CRUD APIs

```
[ Browser / Mobile Client ]
            │
            ▼
    [ Amazon API Gateway ]
    (JWT validation, throttling, caching)
            │
            ▼
    [ AWS Lambda Functions ]
    (CRUD operations / business logic)
            │
            ▼
    [ Amazon DynamoDB / Aurora Serverless ]
```

- Workflow
  - API gateway validates client tokens [via cognito/custom lambda authorizers]
    - routes HTTP methods
    - sync invoke individual lambda functions

- Best for:
  - mobile application backends
  - SaaS REST APIs
  - lightweight microservices

### 2. Async decoupled worker pattern

Used to protect downstream dbs/external APIs from sudden bursts of incoming traffic

```
[ Producer: API Gateway + Lambda ]
                │
                ▼ (Pushes payload in ~50ms)
       [ Amazon SQS Queue ]
                │
                ▼ (Pulls in controlled batches of 1-10)
    [ Worker Lambda Function ]
                │
                ▼
       [ Relational DB / Third-Party API ]
```

- Workflow
  - Instead of writing directly to db, an ingest lambda places the request into an SQS queue and immediately returns `202 accepted` to the client
  - Worker lambda polls SQS with controlled concurrent limits
    - flattening high-traffic spikes into a steady processing stream

- Best for:
  - order checkout processing
  - billing systems
  - 3rd-party webhook ingestion

### Pub/Sub & Fan-out pattern

Used when a single action needs to trigger multiple independent subsystems in parallel

```
                        [ Order Placed Event ]
                                     │
                                     ▼
                            [ Amazon SNS Topic ]
                                     │
         ┌───────────────────────────┼───────────────────────────┐
         ▼                           ▼                           ▼
[ SQS: Inventory Queue ]   [ SQS: Payment Queue ]    [ SQS: Email Queue ]
         │                           │                           │
         ▼                           ▼                           ▼
[ Inventory Lambda ]        [ Payment Lambda ]        [ Email Lambda ]
```

# DynamoDB

- Fully managed, proprietary, highly available with replication across multiple AZs
- NoSQL db with transaction support
- Scales to massive workloads, distributed db
- Millions of req/sec, trillions of rows, 100s of TB of storage
- Fast and consistent in performance [single-digit ms]
- Integrated with IAM for security, authorization, and admin
- Low cost and auto-scaling capabilities
- No maintenance or patching, always available

## Basics

- Tables
  - Dynamodb is made of Tables
  - Each table has a primary key [must be decided at creation time]
  - Each table can have infinite number of items [=rows]

```
| --- primary key -------||-- attributes ---|
|partition_key | sort key|
|    user_id   | game_id | score | result |
| 123          | 999     | 92    | win    |
| 321          | 998     | 34    | lose   |
```

- Items
  - item has attributes
  - can be added over time, can be null
  - maximum item size 400kb
    - larger payloads must be stored in s3 with a reference pointer saved in dynamodb
  - supported data types
    - scalar types: string, number, binary, boolean, null
    - document types: list, map
    - set types: string set, number set, binary set

### Single-Table design or multi-table design

- We pay per table, so a Single-Table design is a well-established pattern in dynamodb
  - since dynamodb is schemaless, items with completely different shapes can sit side-by-side in the same table

- Multi-table design is better for:
  - evolving/unknown access patterns
  - microservices architectures
  - different traffic shapes and lifecycles
  - heavy analytics/data lakes

## Read/Write capacity modes

Control how you manage your table's capacity [read/write throughput]

- Provisioned mode [default]
  - specify the number of read/writes per sec
  - plan capacity beforehand
  - pay for provisioned read capacity units [RCU] and write capacity units [WCU]
  - possibility to add auto-scaling mode for RCU and WCU

- On-demand mode
  - read/writes automatically scale up/down with workload
  - no capacity planning needed
  - pay for what you use, more expensive
  - great for unpredictable workloads, with steep sudden spikes

## How to calculate capacity

- Are you sizing for WCU or RCU?
  - capacity is measured per second

### Calculating WCU [Write capacity units]

- Baseline unit: 1 WCU = 1 standard write/sec item up to 1kb
  - rule: round the item size up to nearest whole 1kb chunk

```
WCU per write = item size in kb / 1 kb // standard
```

Formula

```
total wcu = writes per second * (item size / 1kb) * multiplier
```

- Standard write = multiplier 1x
  - PutItem, UpdateItem, DeleteItem
- Transactional Write = multiplier 2x
  - TransactWriteItems

Ex:

- you need to write 50 items/sec, each item is 2.4kb [standard write]
  - round 2.4kb to 3kb [3 wcus per item]
  - `total wcu = 50 * 3 = 150 wcu`

## Advanced DynamoDB

### DAX [Dynamodb accelerator]

- Fully-managed, highly available, seamless in-memory cache for dynamodb
- Helps with heavy-read traffic
- Microseconds latency for cached data
  - from single-digit ms to microseconds
- Doesn't require application logic change
  - compatible with existing dynamodb APIs
- 5 minutes TTL for cache [default], but can be changed

- DAX vs Elasticache?
  - Dax:
    - individual objects cache
    - query and scan cache
  - Elasticache:
    - store aggregation results
    - more complex, big computation

### Stream processing

- real-time, time-ordered sequence of item modifications [INSERT, MODIFY, REMOVE]
- retained for 24h
- standard trigger for aws lambda
- use cases:
  - react to changes in real-time [welcome email to users]
  - real-time usage analytics
  - insert into derivative tables
  - implement cross-region replication
  - invoke aws lambda on changes to dynamodb table

Example architecture

```
        create/update/delete                                    processing layer    |----> [messaging, notifications] ---> SNS
application -------> dynamodb table ---> dynamodb streams ----> lambda / ec2 / etc ----->  [filtering, transforming] ----> DDB table
                         |                                      |
                         |                                      |   |-------------[analytics] ---> amazon redshift
                         |----- Kinesis data stream ----> Kinesis data firehose --[archiving]--> S3
                                                                |---|-------------[indexing] ---> amazon opensearch
```

### Global tables

- make dynamodb table accessible with low latency in multiple regions
- Active-active replication
- Applications can READ/WRITE to the table in any region
- My enable dynamodb streams as a pre-req

```
table                                       table
us-east-1 <----[two way replication]----> eu-central-1
```

- If dynamodb is already serverless, why would we need global tables?
  - dynamodb is already multi-az by default
  - global tables solve multi-region, not multi-az
    - standard dynamodb is bound to a single aws region
    - from 99.99% availability to 99.999%

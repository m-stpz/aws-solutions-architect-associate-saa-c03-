# Lambda@Edge vs. CloudFront functions

## Edge functions

- Edge functions = serverless functions that run at CND [Content Delivery Network]
  - they run at edge locations, rather than in a centralized cloud data center region [ex: `us-east-1` or `eu-central-1`]
  - instead of routing every user request back to the origin region, they process the request physically closest to the end user
  - typically executing 10-50ms of network rount-trip time

```
[ TRADITIONAL REGIONAL SERVERLESS ]
User in Tokyo ──(150ms round-trip across Pacific)──> us-east-1 (Virginia)
                                                       [ Lambda Function ]
                                                       [ DynamoDB / RDS ]

─────────────────────────────────────────────────────────────────────────────

[ EDGE SERVERLESS ]
User in Tokyo ──(5ms local hop)──> Tokyo Edge PoP (CDN) // PoP = point of presence
                                     [ Edge Function ] (Executes immediately)
                                     ├─ Immediate response, OR
                                     └─ Forwards to origin if needed
```

- Edge PoP / Edge Point of Presence
  - localized facility, data center, network node placed physically close to end-users instead of a distant, centralized data center
  - reduced latency
  - caches content
  - offload core networks
  - handles security

### Usage of edge functions

- URL rewriting and SPA routing
- Security and header injection
- Geo-routing and localization
- Edge auth and token verification
- A/B testing and feature flags

## Edge compute in AWS: CloudFront functions vs. Lambda@Edge

- CloudFront functions:
  - ultra-fast, lightweight operations
  - no network needed [header tweaks, URL redirects, cache-key normalization]
  - lightweight functions written in js
  - use cases
    - cache key normalization: transform req attributes [headers, cookies, query strings, URL] to create optimal cache key
    - header manipulation: insert/modify/delete HTTP headers in req or res
    - URL rewrites/redirect
    - request authentication and authorization: create and validate user-generated tokens [ex: JWT] to allow/deny requests

- Lambda@Edge:
  - operations needing external data or heavier logic
  - calling a db, validating external auth tokens via HTTP, fetching dynamic configs
  - use cases
    - longer execution time [several ms]
    - adjustable CPU/memory
    - code needs 3rd-party libs [ex: AWS SDK to access other AWS services, external API call]
    - network access to use external services for processing
    - file system access or access ot the body of HTTP requests

```
[ Viewer ]
    │
    ▼ (Viewer Request)
[ CloudFront Functions ]  <-- Runs at 600+ Edge PoPs (sub-millisecond JS)
    │
    ▼
[ Lambda@Edge ]           <-- Runs at Regional Edge Caches (Node.js/Python, full network)
    │
    ▼ (Origin Request)
[ S3 / ALB / API Gateway Origin ]
```

| Dimension              | CloudFront func                                  | Lambda@Edge                                                 |
| ---------------------- | ------------------------------------------------ | ----------------------------------------------------------- |
| Execution point        | All 600+ CloudFront edge PoP                     | Regional edge caches [~13 regional centers]                 |
| Runtime                | js [lightweight engine]                          | Node.js, python                                             |
| Network access         | none [can't make external HTTP requests/hit dbs] | Full network access [can call external APIs, DynamoDB, etc] |
| Scale                  | millions req/sec                                 | thousands req/sec                                           |
| Access to request body | No [headers/URL only]                            | Yes [can read and mutate req/res bodies]                    |

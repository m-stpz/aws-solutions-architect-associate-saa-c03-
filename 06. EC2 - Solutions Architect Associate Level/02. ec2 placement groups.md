# EC2 Placement groups

- You can control how the EC2 placement strategy happens
  - This can be defined through placement groups
- When you create a placement group, you define ONE of the following strategies:
  - Cluster: clusters instances into a low-latency group in a single AZ
  - Spread: spreads instances across underlying hardware
    - max 7 instances per group per AZ
    - critical applications
  - Partition: spreads instances across many different partitions within an aZ
    - scales to 100s of EC2 instances per group (hadoop, cassandra, kafka)

## Cluster

- Physical layout: packs instances together inside a single AZ
  - places them on the same/adjacent rack
- Core goal: maximum network throughput and ultra-low network latency
- Primary trade-off: high blast radius (if one fails, all instances can go down together)

Pros

- Great network
- low-latency, high throughput

Cons

- If the AZ fails, all instances come down with it
- High blast radius

Use case

- Big data job that needs fast completion
- Application that needs extremely low latency and high network throughput
- Distributed machine learning & deep learning training
- High-performance computing
  - weather forecasting
  - computation fluid dynamics (CFD)
  - molecular dynamics simulations
- Low-latency in-memory data grids
  - high-throughput Redis/memchaced clusters

## Spread

- Physical layout: places each instance on distinct physical hardware racks:
  - each with its own network switch and power supply
- Core goal: maximum blast-radius isolation
- Primary trade-off: Increased latency, yet lower blast radius

Pros

- Can spread across AZ
- Reduced risk of simultaneous failures
- EC2 instances are on different physical hardware

Cons

- Limited to 7 instances per placement group

Use case

- Applications that need high availability
- Critical applications
  - critical primary db
  - core infrastructure nodes

# Summary

- Since in this chapter, there's a lot of new concepts, I've decided to do a little summary to keep them fresh

## Core block and Image concepts

### 1. EBS (Elastic Block Store)

- Network-attached block stored for EC2 instances

> A virtual hard drive connected over the network

- AZ Bound
  - To move the ebs volume from another AZ, you must take a snapshot and recrete the volume there

- Lifecyle: Independent of EC2 instance lifecycle
  - if configured properly (disabled `DeleteOnTermination`), data persists even when instance is terminated

- Scaling: dynamic capacity and performance adjustments (volume type, size, IOPS)

#### 1.2 EBS Snapshots

- Point-in-time backups of EBS volumes stored durable in S3
  - managed under the hood by AWS

- Cross AZ and Cross region
  - good for disaster recovery (DR) and environment replication

- FST (Fast snapshot restore): eliminates latency on initial block reads when restoring volumes from snapshots

#### 1.2 EBS Volume types

| Category                   | volume type       | dominant use case                         | performance metrics      | key characteristics                                                     |
| -------------------------- | ----------------- | ----------------------------------------- | ------------------------ | ----------------------------------------------------------------------- |
| General purpose            | gp3               | system volumes, dev/test, dbs             | up to 16k IOPS / 1K mb/s | cost-effective; IOPS and throughput scale independently of storage size |
|                            | gp2               | legacy system volumes                     | up to 16k IOPS           | baseline IOPS tied to volume size                                       |
| Provisioned IOPS (SSD)     | io1/io2           | mission-critical dbs                      | up to 64k IOPS           | high consistency, low-latency; supports EBS multi-attach                |
|                            | io2 block express | ultra-high workload                       | up to 256k IOS/ 4k mb/s  | sub-millisecond latency; massive enterprise dbs                         |
| HDD (Throughput optimized) | st1               | big data, data warehouses, log processing | up to 500 mb/s           | high throughput for large, sequential IO; can't boot a volume           |
| HDD (Cold)                 | sc1               | cold data, infrequently accessed logs     | up to 250 mb/s           | cheapest; cannot boot a volume                                          |

#### 1.3 EBS multi-attach

- Allows attaching a single io1/io2 volume to multiple EC2 instances (up to 16) WITHIN the SAME AZ
- Requires cluster-aware file system (e.g. GFS2, OCFS2)

#### 1.4 EBS encryption

- Encrypts data at rest inside the volume
  - also in
    - transit between instance -> volume
    - snapshots created from the volume
    - volumes restored from those snapshots

- KMS Integration: handled transparently using AWS KMS (Key managemenr Service) with negligible performance impact
- Handling unencrypted volumes: you can't encrypt an existing unencrypted volume. Instead:
  1. create snapshot
  2. copy snapshot while selecing encryption
  3. launch a new volume from the encrypted snapshot

### 2. AMI - Amazon Machine Image

- Pre-config template to launch EC2 instances
  - contains OS, app server, software stack, launch permissions, block device mappings

- Key components
  - root volume template
  - architecture config

- Region-specific
  - to launch an EC2 instance in another region using the AMI, you must first copy it to the target region

### 3. EC2 Instance store

- High-performance block storage physically attached to the server running the EC2 instance
- Ephemeral data: data DOES NOT persist through termination or stopping
- EBS is like a network hard drive, while EC2 instance is the SSD

#### 3.1 EC2 Instance store vs. EC2 Multi-attach vs. EFS

- All of them allow multiple servers/applications to read/write data

- EC2 Instance store: local, temporary, single-instance performance monster
- EB2 Multi-attach: shared raw storage block for tight server clusters **in one location**
- EFS: Managed network file system shared **across regions**

| Feature              | EC2 Instance store                                    | EBS multi-attach                  | EFS                                         |
| -------------------- | ----------------------------------------------------- | --------------------------------- | ------------------------------------------- |
| Physically it's a... | local SSD drive inside the physical hypervisor server | Network-attached SAN block volume | Managed cluster file server                 |
| Data persistence     | ephemeral                                             | persistent                        | persistent                                  |
| Connection capacity  | 1 instance                                            | 16 instances                      | 1000s of instances (and containers, lambda) |
| Geographic scope     | single physical server host inside 1 AZ               | single AZ                         | Multi-AZ                                    |

## Network file system & direct comparison

### 4. EFS (Elastic File System)

- Fully managed, serverless, POSIX-compliant network file system
- Multi AZ win a region
- Concurrent connections
  - 100s to 1ks of EC2 instances can concurrently mount an EFS volume across different AZs
- Scales automatically
  - pay-per-use
  - no pre-provisioning
- Supported on Linux instances

# Quiz - Monitoring and Auditing

1. You have an RDS DB instance that's configured to push its database logs to CloudWatch. You want to create a CloudWatch alarm if there's an Error found in the logs. How would you do that?

- Create a CW logs metric filter that filter the logs for the keyword `Error`, then create a CW alarm based on that metric filter
  - why?
    - log ingestion: RDS instance pushes its db logs into a CW log group
    - metric filter: metric filter is attached to that log group with the filter pattern "Error"
      - every time a log event containing Error arrives, CW increements a custom numerical metric
    - cloudwatch alarm: create a standard CW alarm watching that custom metric
      - when sum >= 1 for instance within 1/5-minute period
      - config it to send a notification via SNS topic

- RDS -> CW log group -> metric filter transforms the findings into numbers -> numbers generate an alarm based on their rules
  - why not?
    - scheduled event + lambda scanning the logs?
      - wrong requirement: prompt asks for CW alarm
      - this approach bypasses CW alarms and jumps straight to sending an SNS message from lambda
    - poor architecture
      - polling logs every hour introduces a 60-min delay in detecting errors
      - requires writing and maintaining custom code
      - incurs unnecessary lambda execution and CW logs API when a native, zero-code, real-time feature already exists

2. You have an application hosted on a fleet of EC2 instances managed by an Auto Scaling Group that you configured its minimum capacity to 2. Also, you have created a CloudWatch Alarm that is configured to scale in your ASG when CPU Utilization is below 60%. Currently, your application runs on 2 EC2 instances and has low traffic and the CloudWatch Alarm is in the ALARM state. What will happen?

- CW alarm will remain in ALARM state but never decrease the number of EC2 instances in the ASG
  - if you set ASG to have min. capacity 2, it can't go below it, even if in theory the CW alarm would trigger and EC2 instance termination

3. How would you monitor your EC2 instance memory usage in CloudWatch?

- Use the unified CW agent to push memory usage as a custom metric to CW
  - why?
    - AWS treats EC2 memory utilization as an OS-level [guest] metric, rather than a hypervisor-level metric
    - AWS hypervisor doesn't inspect the contents of an instance's guest OS memory for security and isolation reasons
      - thus, CW can't see how much RAM is actively used

| Metric category                   | Examples                                                                                             | How CW gets it                                                                                                  |
| --------------------------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Default host / hypervisor metrics | CPU usage, network in/out, disk read/write ops [instance store], status checks                       | Automatically by AWS at 5-min intervals [free] with zero setup                                                  |
| Default OS / guest-level metrics  | Memory [RAM] usage, swap usage, disk space usage [EBS volume free/used space], running process count | requires installing and configuring the unified CW agent inside the EC2 instance to push them as custom metrics |

- why not?
  - enable EC2 detailed monitoring
    - detailed monitoring only changes the REPORTING FREQUENCY of DEFAULT HYPERVISOR metrics from 5-min to 1-min
    - adds additional fee
    - it doesn't unlock any new OS-level metrics like RAM or disk space
  - by default, EC2 instance pushes memory usage to CW
    - false, EC2 instance don't collect or push memory metrics out of the box
    - without CW agent [and an IAM instance profile gratingin `CloudWatchAgentServerPolicy`], CW has zero visibility into RAM usage

5. Someone has terminated an EC2 instance in your AWS account last week, which was hosting a critical database that contains sensitive data. Which AWS service helps you find who did that and when?

- CloudTrail
  - log, monitor, retain account activity related to AWS infra
  - history of API calls made through UI, SDK, and CLI

6. You have CloudTrail enabled for your AWS Account in all AWS Regions. What should you use to detect unusual activity in your AWS Account?

- CloudTrail insights
  - creates a baseline of what "normal" looks like
  - anomaly identifications
    - API call rate insights: sudden spike in mutating/write API calls
    - API error rate insights: a suggen surge in failed API calls
  - structured alert payload: payload containing...
    - baseline average
    - observed spike average
    - specific API name
    - top IAM principals driving the spike
    - top error codes

- why not?
  - CloudTrail management events
    - record raw control-plan API calls
    - raw log lines, not automatic detection/flagging of unusual patterns without an analysis layer on top
  - CloudTrail data events
    - track high-freq object/functions executions instead of control-plan anomalies
    - provide raw logs rather than behavioral anomaly detection

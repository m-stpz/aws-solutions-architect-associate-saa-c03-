# Routing policy

- Define how route 53 responds to DNS queries
- Careful with the word "routing"
  - not the same as LB routing, which routes traffic
  - DNS doesn't route any traffic, it only responds to DNS queries

## Policies

### Simple

- single resource per record or returns multiple random IP addresses for basic client-side round-robin
  - doesn't support health checks for traffic shifting
- route traffic to a single resource
- can specify multiple values in the same record
- if multiple values are returned, a random one is chosen by the client

```
# single value

client --- foo.example.com ---> Amazon
       <--- 12.34.56.78 ------- route 53


# multiple values: client chooses randomly

client --- foo.example.com ---> Amazon
       <--- 12.34.56.78 ------- route 53
            11.22.33.44
            99.88.77.66
```

- when alias is enabled, specify only one AWS resource

### Weighted

- routes traffic across multiple endpoints based on assigned % weights
  - 80% for v1 and 20% for v2 for canary deployments or gradual rollouts
- control the % of requests that go to each specific resource
- assign each record a relative weight
  - weights don't need to sum up to 100

```
traffic (%) = weight for a specific record / sum of all the weights for all records
```

- DNS records must have the same name and type
- Can be associated with health checks
- Use cases: load balancing between regions, testing new application versions...
- weight = 0 -> resource won't receive traffic
- all records weight = 0 -> all records return equally

### Failover

- uses health checks to implement active-passive failover
  - queries route to primary endpoint until it becomes unhealthy
  - then route 53 automatically switches DNS responses to secondary/DR endpoint

- We select
  - primary
  - secondary
  - associate it with a health check

### Latency-based

- Directs users to AWS region with lowest network latency for that specific user
- Redirects the user to the smallest possible latency to the resource
- Very helpful when latency for users is a prio
- Latency is based on traffic between users and AWS regions
- As of know, when adding the latency based routing, you need to specify the region of the IP
  - AWS doesn't recognize it automatically as of now

### Geolocation = Political/Administrative Boundaries [Political borders]

- traffic is routed based on the geographic location of that user
  - useful for localizing content, language selection, restrict content distribution, load balancing, or legal compliance
- Routing based on user location
- Different from latency-based
- Specify a location by: continent, country or state
  - if there's overlapping, most precise location is selected
  - ex: All my Asia users should go to...
- Should create "Default" record, in case there's no match on location

### Geoproximity = Physical distances/coordinates [Latitude and longitude + bias]

- traffic is routed based on the geographic location of users and resources
  - bias parameter = expands/shrinks physical traffic radius directed to a specific region
- route traffic to resources based on the geographic location of users and resources
- Ability to shift more traffic to resources based on the defined bias
- To change the size of the geographic region, specify bias values:
  - to expand: 1 to 99, more traffic to the resource
  - to shrink: -1 to -99, less traffic to the resource
- Resources can be:
  - AWS resources (specify AWS region)
  - Non-AWS resources (specify latitude or longitude)
- Must use route 53 traffic flow (advanced) to use this feature

### Multi-value answer

- returns multiple healthy IP addresses selected at random
  - supports health checks to filter out failed endpoints
- Use when routing traffic to multiple resources
- Route 53 return multiple values/resources
- Can be associated with health checks
  - return only values for healthy resources
  - up to 8 healthy records are returned for each multi-value query

### IP-based

- routes traffic based on client CIDR blocks
  - useful for optimizing traffic from specific ISPs or private corporate subnets
- Routing is based on client's IP addresses
- Provide a list of CIDRs for your clients
  - and corresponding endpoints/locations
  - user-IP-to-endpoint mappings
- Use cases: optimize performance, reduce network costs
- Ex: route end users from a particular ISP to a specific endpoint

## Latency (fastest ping response) vs. geolocation (political boundaries) vs. geoproximity (coordinates)

Core difference relates to the metric used for routing decision:

- Latency: based on network speed / ping time (ms)
  - when to use it? performance is top prio
  - fastest possible experience
  - closest physical location might not be the lowest latency route
    - telecommunications infra, internet routing hops, submarine cables, congested traffic, etc
- Geolocation: based on user's political boundaries (continent, country, US state)
  - when to use it? compliance and data sovereignty, localization, geo-restrictions
- Geoproximity: based on physical geographic distance between user and infra, with adjustable bias to increase/shrink boundaries
  - when to use it:
    - controlled traffic shifting / migration: moving traffic from a data center in London to Frankfurt without hard cutovers
    - capacity management

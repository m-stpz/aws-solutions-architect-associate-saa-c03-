# Cache invalidation

Instead of relying on TTL, we can use "smart" cache invalidation techniques

## 1. Event-driven targeted invalidation: industry standard

Instead of invalidating the whole cache `/*`, invalidate only the specific resource path when a write happens

```
author updates blog "123"
|---> lambda [UpdateBlog]
        |---> writes to dynamodb
        |---> calls CloudFront API: CreateInvalidation(["/blogs/123", "/blogs/123/*"])
```

- invalidations propagate globally in ~15 to 60s
- for something that is rarely updated, this is more than fine
- if `blogs/123` has sub-resources, `blogs/123/*` counts as one single invalidation path

## 2. Cache-tag invalidation: Surrogate-Keys

CloudFront supports invalidation by cache takes. When lambda serves `GET /blogs/123`, it includes response header

```
Cache-Tag: blog-123, author-45, tech-category
```

- When blog 123 changes, call the invalidation API using `#blog-123`
  - CloudFront purges the cached page associated with that tag

## 3. Content hashing: versioning of assets

- For images, CSS, and JS, NEVER USE CACHE INVALIDATION. Embed content hashes into URLs

```
/images/header-<hash-1>.webp
```

- Give versioned assets a 1-year TTL: `Cache-control: public, max-age=<1year>, immutable
- When image updates, upload a new file with new hash: `header-<hash-2>.webp and update the blog post to point to the NEW URL

# Classic Architectures

- Foundational, multi-tier patterns that dominated cloud computing before the widespread adoption of serverless or container orchestration became standard practice
- They remain highly compatible with legacy applications, and offer granular control over the infra

## Architecture 1: Scalable multi-tier web application [MVC]

- Separates the application into distinct logical layers
- Model/Data: Db
- View/Presentation: Web
- Controller/Application: Logic

- Key components
  - Elastic Load Balancing [ELB]: distributes incoming traffic
  - Auto Scaling Group [ASG]: ensures ec2 instances scale up/down based on demand
  - Amazon RDS

```
[ Public Internet ]
                |
                V
+----------------------------------+
|  Application Load Balancer (ELB) |  <-- Entry point, distributes traffic
+----------------------------------+
                |
                | (Traffic distributed across AZs)
        /-------+-------\
+----------------+ +----------------+
| Public Subnet  | | Public Subnet  |  <-- In different Availability Zones
| (AZ A)         | | (AZ B)         |
|                | |                |
|  [Web Server]  | |  [Web Server]  |  <-- Stateless EC2 Instances
+----------------+ +----------------+
        |                  |
        | (Internal Security Group Traffic)
        V                  V
+----------------------------------+
| Internal Load Balancer (Optional)|  <-- For larger, complex apps
+----------------------------------+
        |
        |
+----------------------------------+
| Private Subnet (APP Layer)       |
| [Application Server] <----------> [Application Server]
| (Scaling Group)                  |  <-- Business logic, connects to DB
+----------------------------------+
                |
                | (Database connection)
                V
+----------------------------------+
| Private Subnet (DB Layer)        |
| [Amazon RDS (Master)] <--------> [Amazon RDS (Standby)]
| (Multi-AZ Deployment)            |  <-- Persistent Storage
+----------------------------------+
```

### How it works

1. User hit the LB [public subnet]
2. ALB forwards traffic to web servers running in an ASG
   - across multiple AZs for high availability
3. Web servers handle static content and proxy dynamic requests to application servers
   - often the same EC2 instance type, just different logical tier
4. Application servers connect to the Amazon RDS db
   - configured for multi-AZ replication for durability and failover

## Architecture 2: public-facing website with static s3 hosting

- Evolution of the first architecture
- Optimized for cost and performance
- It offloads heavy lifting of static content delivery from expensive EC2 instances

- Key components
  - S3: Stores static assets [HTML, CSS, JS, images]
  - CloudFront: CDN that caches S3 content closer to users
  - Route 53: DNS routing

```
USER (Browser)
  |
  | 1. DNS Request
  V
[ Amazon Route 53 ]
  |
  | 2. Resolves to CloudFront URL
  V
+-------------------------+
| [ Amazon CloudFront ]   | <--- Global CDN Edge Locations
| (Global Cache)          |
+-------------------------+
  |
  | 3. Cache Miss (Fetches content)
  V
+-------------------------+     +-------------------------+
| [ Amazon S3 Bucket ]    |     | [EC2 / Lambda / API GW] |
| (Static Website Hosting)|<--->| (Dynamic API Backend)   |
| (HTML, CSS, Images)     |     | (JSON Data)             |
+-------------------------+     +-------------------------+
```

### How it works

1. User's browser requests the website via Route 53
2. Route 53 directs user to nearest CloudFront edge location
3. CloudFront serves cached static assets directly from s3
   - extremely cheap and fast
4. If the application requires dynamic data (ex: logging in, fetching user data), the frontend JS in the browser makes API calls directly to the backend
   - backend: EC2/ASG or API Gateway/Lambda

## Architecture 3: The Asynchronous Backend Processing Job

- Used when a user request triggers a long-running task
  - video processing
  - generating large report
  - sending bulk emails
- We don't want the user to wait for that task to finish
  - acknowledge the request
  - process the task in the background

- Key components
  - SQS: message queue, the buffer
  - ASG: workers that process the queue
  - DynamoDB/RDS: storage for results

```
                                       +-----------------+
                                       | [ CloudWatch ]  | <--- Monitors Queue
                                       | [ Alarms ]      |
                                       +-----------------+
                                              |
                                              | 5. Scale Trigger
                                              V
+-------------+        +----------+        +------------------+
| Front-end   | 1. Add | SQS      | 3. Poll| Back-end         |
| Web Server  |------->| Queue    |<-------| Worker Fleet     |
| (EC2/Lambda)|  Task  | (Standard|        | (ASG of EC2)     |
+-------------+        | or FIFO) |        +------------------+
                        +----------+           |           |
                                               | 4. Process| 6. Save
                                               V           V
                                       +-----------------------------+
                                       | [ Amazon DynamoDB / RDS ]   |
                                       | (Results Store)             |
                                       +-----------------------------+
```

### How it works

1. Frontend/web server receives a user request
2. Instead of processing the video sync, frontend writes a message [some relevant data for it to be processed] into the SQS queue

- frontend immediately returns "job accepted"

3. A separate fleet of backend worker servers [in an ASG] polls the SQS queue
4. When a worker sees a message, it picks it up, locks it, and begins the processing
5. CloudWatch monitors the SQS queue length

- if queue grows, it triggers the ASG to add more workers

6. Once finished, the worker saves the result to the db and deletes the message from the SQS queue

# Basic Networking AWS

- AWS networking is built around software-defined networking model
- It mimics traditional on-prem networking, while offering massive scalability, flexibility, and automated management

## SSH [Secure Shell]

- Network protocol used to secury connect to, control and transfer files with a remote compute, usually a linux server over an unsecured network, like the internet

- Primary way to interact with servers
  - remote CLI execution: through the CLI we can install packages, inspect logs, restart services and manage files
  - encrypted file transfers

### Commands

```bash
# generate a modern SSH key pair
ssh-keygen -t ed25519 -C "mateus@macbook"

# connect to server
ssh -i ~/.ssh/my-aws-key.pem ec2-user@<ip>

# copy a local file to a remote server
scp -i ~/.ssh/my-aws-key.pem ./docker-compose.yml ec2-user@<ip>:<path>
```

## VPC - Virtual private cloud [Fence around resources / the campus]

- Logically isolated, private virtual networking
- A fence around a bunch of resources
- It separates some resources from others

### CIDR [Classless Inter-Domain Routing]

- /24: affects last octet
  - `10.0.0.1` to `10.0.0.254`
  - standard, ideal size for creating individual subnets [public or pviate] inside a VPC
- /16: affects last 2 octets
  - `10.0.0.1` to `10.0.255.254`
  - typically recommended size for the main CIDR block of an AWS VPC
- /8: affects last 3 octets
  - `10.0.0.1` to `10.255.255.2554`
  - usually used for large enterprise network or massive infra architecture

## Subnets [Segmentation of resources / the building]

- A range of IP addresses within your VPC that allows us to segment the network
- While a VPC would be a large gated campus, the subnet is the individual building or department inside the campus
- Reside within an single AZ
  - for AZ, we replicate the setup across at least two AZs

### Public vs. Private

- Public: the front desk
  - resources here can send and receive traffic from the public internet
  - they must have public/elastic IP addresses
  - accept direct inbound connections from the internet
    - ALB, bastion hosts, NAT gateways
- Private: the R&D lab
  - don't have a direct route to the internet
  - resources here are isolated from external traffic
    - application servers, microservices, dbs
  - if a resource here needs outbound internet access, it routes through a NAT [Network address translation] gateway

- To launch resources, you need a subnet

### Standard Multi-AZ architecture [4 subnets]

- High availability
- 2 AZs

- AZ 1
  - public subnet:
    - internet-facing components, ex: ALB or public NAT gateway
    - 10.0.0.0/24
  - private subnet:
    - internal backend services or primary dbs
    - 10.0.1.0/24
- AZ 2
  - public subnet
    - redundant public-facing entry points
    - 10.0.2.0/24
  - private subnet
    - hosts secondary/replica backend services or dbs
    - 10.0.3.0/24

## Gateway: Connects VPC to another network

AWS has various specialized gateways to control how traffic enters and leaves a VPC

- Internet gateway: allows communication between your VPC and the public internet
  - you need this for your VPC connect to the internet
  - one IGW [internet gateway] per VPC
  - acts as target in your tourtable for internet-routable traffic
  - performs 1-1 network address translation [NAT] between EC2 isntance private ipv4 address and its public ipv4 address

- NAT [Network Address Translation] Gateway: allows a private subnet to connect to the internet or other AWS services
  - however, it prevents the internet from initiating connections back to those instances
  - instances in a private subnet don't have public IP address, so they can't use IGW
  - they still need outbound internet access to download OS patches, pull docker images, or call 3rd-party APIs
  - deploy a NAT gateway inside a public subnet and attach a static elastic ip [EIP] to it

- Virtual private gateway: connect your VPC to your on-prem data centers

## Route Tables | Traffic directors

- Set of rules/routes that determines where network traffic is directed from your subnets or gateways
- Every subnet must be associated with a route table
  - a subnet is not inherently "public" or "private" because of a checkbox
  - it's defined by its route table
- Route tables belong to the VPC and are associated with a subnet

## Network security: Security Groups vs. Network ACLs

- We can control traffic at both the instance level and the subnet level

| Feature         | Security groups                                                                                            | Network ACLS [NACLs]                                                          |
| --------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Scope           | operates at the instance/NIC level                                                                         | operates at the subnet level                                                  |
| State           | stateful: if you send a request out, the response is automatically allowed in, regardless of inbound rules | stateless: both inbound and outbound traffic rules must be explicitly defined |
| Rule evaluation | evaluates all rules before deciding whether to allow traffic                                               | evaluates rules in a strict numerical order                                   |

## Hands on

To launch and ec2 instance in both subnets and have the architecture work, we must

1. Create the VPC and internet gateway

- Create a VPC with CIDR `10.0.0.0/16`
- Create an internet gateway and attach it to the VPC

2. Create public and private subnets

- Create `public-subnet-a`: 10.0.1.0/24
- Create `private-subnet-a`: 10.0.2.0/24
- Both in the same AZ
- Enable auto-assign public ipv4 address on the public subnet settings
  - thus instances launched there receive public IP automatically

3. Provision NAT gateway

- Allocate an Elastic IP, then launch a NAT gateway inside `Public-Subnet-A`
- Wait for the status to become `Available`

4. Configure and associate route tables

- Create two custom route tables
  - Public-RT: add route `0.0.0.0/0` -> `igw-id`. Associate with `Public-Subnet-A`
  - Private-RT: add route `0.0.0.0/0` -> `nat-id`. Associate with `Private-Subnet-A`

5. Create security groups

- Public-SG: allow inbound HTTP/HTTPS [80/443] from `0.0.0.0/0` [or SSH 22 from your specific IP]
- Private-SG: allow inbound app traffic [ex: port `3000` or `22`] only from `Public-SG`

6. Launch EC2 instances

- launch the public EC2 in `Public-Subnet-A` with `Public-SG` [auto assigned public IP enabled]
- launch private EC2 in `Private-Subnet-A` with `Private`SG`

```
AWS Cloud ------------------

VPC --------gateway---------
               |
            router ---------- // every VPC has a router
                            |
    ----------------------[route table]
    Private   --------    Public  // the communication between your subnets is setup by default
    Subnet                Subnet
                          EC2 instance
```

## The flow

- Public

```
user browser -> IGW -> Public-RT -> Public-SG -> Public EC2
```

- Private

```
Private EC2 -> Private-RT -> NAT gateway -> Public-RT -> IGW -> Internet
```

## Containers

- Operate almost identically to the EC2 instances at the network layer
  - public subnet: ALB and NAT gateways
    - without a NAT gateway, the Fargate can't pull docker images from ECR/Docker hub and fetch secrets from secret manager
  - private subnet: fargate tasks / EKS pods
    - they don't get a public IP

## Lambda

- Default: Non-VPC lambda -> access public internet, but not your VPC
  - when creating a lambda without setting VPC settings:
    - it runs inside a VPC managed by AWS, not yours
    - internet access: built-in. It can immediately call 3rd party APIs and public AWS APIs
    - it can't reach private resources inside your VPC

- VPC-connected lambda -> access to your VPC, but not the public internet
  - to get lambda to query a private RDS db or Redis cluster, attach it to your VPC by specifying subnets and security groups
  - AWS creates a Hyperplane ENI inside your chosein private subnet and routes your lambda traffic through it
  - the moment you attach it to your VPC, it loses
    - how to restore internet/AWS access
      - put the lambda in private subnets whose route tables point to `0.0.0.0/0` to a NAT gateway
      - add VPC endpoints [gateway endpoints for s3/dynamodb, interface endpoints for secrets manager/SQS] so the lambda can reach AWS services privately without paying NAT gateway data charges

Rule of thumb:

- keep lambda functions outside VPC unless they explicitly need to talk to private VPC resources [RDS/Redis]
- for containers [Fargate/EKS] always place tasks in private subnets behind a public ALB and pair VPC endpoints [for ECR, S3, CloudWatch logs, and Dynamodb] with a NAT gateway to keep image pulls fast and NAT bills low

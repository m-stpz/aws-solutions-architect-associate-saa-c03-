# Cloud computing

## Scaling

### Vertical

Increase the node's

- CPU
- Memory
- Disk

> As you vertically scale your application, you get diminishing returns in terms of cost

Pros

- Simpler to implement and understand

Cons

- Cost has diminishing returns
- Low stability

### Horizontal

- Smaller machines hosted in a spreaded manner

Pros

- Stability
- Lower cost

Cons

- More complex

## Load balancing

- How do you send traffic to the different machines [in horizontal scaling]?
- How do you know that these machines are healthy to receive traffic?

- This is where load balancing is for
  - distributes the traffic to one of the available hosts
  - routes traffic to the instances of your application

## Auto scaling

- Automatically add/remove instances according to traffic

### Serverless

- Originally: we can create a function and have it run without any idea of the underlying infrastructure
  - AWS Lambda
    - backend API/script
    - initially there was EC2
      - most people don't want to manage the instance [OS, security, quantity], then AWS introduced lambda
      - people want to write the code, it doesn't matter where it's running, only that it runs
      - you don't know about the underlying EC2 instances that are running under the hood
- Now: the idea of not worrying about the underlying infra and only using the service
  - OpenSearch

## Event-driven architecture [EDA]

- Before EDA, we'd do things synchronously:
  - request/response (model) between the different services
  - sequential
  - order -> charge -> warehouse -> fraud ...

- Request/response creates tight coupling between the dependencies/services
  - then, EDA comes as a way to loosen this tight coupling

- Instead of sync, we use async tasks
  - a message to a notification engine
  - the broker sends the message to all subscribers of this topic
  - this way, the service that triggered the event doesn't need to know about the downstream consumers of it

- EDA adds decoupling at the cost of increased complexity
  - what if a given service fails it?
    - we need to have compensating actions

- Publisher: The event that creates the messages

- Subscriber: The downstream consumers of the message

## Container Orchestration

- Container: Isolated environment
- You can host your container on an EC2 instance, however, you'd need:
  - to monitor it
  - if it crashed, recover it
  - it adds the maintainability complexity

- Then, container orchestration comes as a solution to it (ECS/EKS)
  - two flavors of the same solution
  - they make it much easier deploying and manage container based applications

## Storage

1. Object-storage: media files, json objects, csv, blob

- dumping ground in which you can dump data and access later

2. Block storage: volumes (HDD/SSD)
   - cloud providers offer auto scaling on it

3. DBS: relational, nosql dbs [document-model], and caches

> cache is kind of a subjective discussion of whether it's considered a db

## Availability

- How often is our application is up and running within a time window
- How do you make your application available?
  - horizontal scaling [instances + load balancers]
  - different AZs [physically separated data centers]
  - separated physical infra [e.g, power grid, backup generators, cooling systems, physical security]

## Durability

- When you store data, it should be retrievable
  - the data should be safe from being lost/erased
  - data recovery

## IaC [Infrastructure as Code]

- First, we'd use the AWS console, clicking stuff around through the UI
  - easy to make mistakes
  - difficult to replicate exactly
  - no "version" control

- Taking the config and instead of clicking the console, you write it as code
  - then, you have it versioned
  - you have it reviewed [prs]
  - easy to replicate [easy to deploy to different places]
  - easy to write [declarative/imperative]

- AWS CloudFormation or CDK

- Terraform is not locked in to a vendor
  - It can be used in Azure, AWS, GCP, etc

## Cloud Networks

- Previously, we'd have a server room in the company
  - the instances will be public and these will be private
  - private subnets would have the private data, the db, etc

- Here, you have subnets, security groups
- You specify to what your instances are allowed to talk with
- You can isolate/expose services at will

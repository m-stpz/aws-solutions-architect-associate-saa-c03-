# Modern architecture

- "Classic" architecture relies heavily on:
  - provisioned virtual machines [ec2]
  - relational db clusters
- "Modern" architectures shift the focus towards:
  - serverless computing
  - container orchestration
  - event-driven decoupling
  - AI integration

## Architecture 1: Zero-server [fully serverless] web and API stack

- Eliminates server management entirely
- Scales instantly from zero to millions of requests
  - pay only for the exact ms compute time consumed

- Key components
  - CloudFront & S3: front-end hosting [react, angular, vue SPAs]
  - API gateway: manages, throttles, and routes HTTP/Webscoket endpoints
  - Lambda: executes backend business logic on-demand
  - Amazon DynamoDB: a fully managed, single-digit ms NoSQL db

```
USER (Browser / SPA)
  |
  +---> [ CloudFront + S3 ] ---------> (Loads HTML, JS, CSS frontend)
  |
  | (API Requests: REST / GraphQL)
  V
+----------------------------+
| [ Amazon API Gateway ]     | <--- Handles auth, throttling, routing
+----------------------------+
         |
         | (Triggers code execution)
         V
+----------------------------+
| [ AWS Lambda Functions ]   | <--- Stateless business logic
+----------------------------+
         |
         | (Reads/Writes data)
         V
+----------------------------+
| [ Amazon DynamoDB ]        | <--- Serverless NoSQL Database
+----------------------------+
```

### How it works

1. User's browser loads the frontend application straight from a global CDN [CloudFront/S3]
2. Actions in the app trigger API requests to API gateway
3. API gateway instantly spins up AWS lambda functions to handle the payload
   - no idle server exists
   - if no one is using the app, compute cost drops to zero
4. Lambda queries/updates db table for sub-10ms data persistence

## Architecture 2: Containerized microservices mesh [ECS/EKS + Fargate]

- Complex, enterprise-grade applications that need `_____`, which don't fit well into Lambda's execution model, containers are the modern standard
  - long-running process
  - complex local state
  - heavy framework runtimes [django/spring boot]

- Key components:
  - ECS [Elastic Container Service] or EKS [Kubernetes]: orchestration engines
  - Fargate: serverless compute for containers [no ec2 instances to patch]
  - SNS / SQS: inter-service messaging and event streaming
  - Aurora serverless: distributed relational db that scales compute capacity up/down

```
                  [ Application Load Balancer ]
                                |
        +-----------------------+-----------------------+
        | (Route by path/domain)                        |
        V                                               V
+-------------------------------+               +-------------------------------+
| ECS / Fargate Cluster         |               | ECS / Fargate Cluster         |
| [ Microservice A: Auth ]      |               | [ Microservice B: Orders ]    |
+-------------------------------+               +-------------------------------+
        |                                                       |
        | (Publish Event)                                       | (Consume Event)
        v                                                       v
+-------------------------------+                       +-------------------------------+
| [ Amazon SNS Topic ]          |---------------------->| [ Amazon SQS Queue ]          |
+-------------------------------+                       +-------------------------------+
                                                                |
                                                                V
                                                        +-------------------------------+
                                                        | [ Aurora Serverless (SQL) ]   |
                                                        +-------------------------------+
```

### How it works

1. incoming traffic hits an ALB and is routed to individual microservices running in isolated containers managed by ECS/EKS on Fargate
2. Services are completely decouples. No HTTP, on messages on queues
   - instead of making sync HTTP calls to each other [cascading failures], microservice A publishes a state change to an SNS topic
3. Microservice B picks up the event async via SQS queue, processes it independently, and updates the aurora serverless db

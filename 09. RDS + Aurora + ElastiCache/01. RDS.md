# RDS - Relational Database Service

- It's a relational db managed by AWS
  - managed db service that uses SQL as query language
- Create dbs in the cloud that are managed by AWS. RDS manages:
  - postgres, MySQL, MariaDB, Oracle, Microsoft SQL server, IBM DB2, Aurora (AWS Proprietary db)

## Why use RDS?

It's managed, thus AWS provides:

- Automated provisioning, OS patching
- Continuous backups and restore to specific timestamp (point in time restore)
- Monitoring dashboards
- Read replicas for improved read performance
- Multi AZ setup for DR (Disaster recovery)
- Maintenance windows for upgrades
- Scaling capabilities (vertical and horizontal)
- Storage backed by EBS

However, we can't SSH into the instances

## RDS - Storage auto scaling

- Increases storage in our RDS DB instance dynamically
- When RDS detects you're running out of free db storage, it scales automatically
- Avoid manually scaling your db storage
- You have a Maximum Storage Threshold
  - maximum limit for db storage
- Automatically modify storage if:
  - free storage is less than 10% of available space
  - Low-storage lasts at least 5 minutes
  - 6 hours have passed since last modifications
- Useful for applications with unpredictable workloads
- Supports all RDS db engines

## RDS Read Replicas vs Multi AZ

Read replicas are for performance (scaling reads), while multi-AZ is for disaster recovery

| Feature             | RDS Read replicas                                        | RDS Multi-AZ                                                                    |
| ------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Purpose             | Read scalability and performance                         | High availability and fault tolerance                                           |
| Replication mode    | Async (eventually consistent)                            | Sync (strong consistency)                                                       |
| Behavior            | Active for reads (applications connect directly to them) | Passive standby (cannot be read from or written to)                             |
| Failover behavior   | Manual (must promote replica to standalone db)           | Automatic (RDS switches DNS automatically in 60-120s)                           |
| Connection endpoint | Has its own separate DNS endpoint for read traffic       | Single DNS endpoint (AWS switches IP underlying IP during failover)             |
| Geographic scope    | Same AZ, Cross-AZ, or Cross-Region                       | Same region only (across different AZs)                                         |
| Backups impact      | Backups are separate (disabled by default on replicas)   | Automated daily snapshots are taken from the standby (no I/O freeze on primary) |

When to use...

- Read replicas
  - production db is read-heavy and the primary CPU is spiking
  - running heavy analytical, reporting or BI queries and we want to avoid locking tables/slowing down db
  - cross region replicas to lower read latency for global users

- Multi-AZ
  - need zero downtime failover
  - automated db OS patching and maintenance without taking application down
  - automated backups without taking I/O performance on prod db

### RDS Read Replicas

- Up to 15 read replicas
- They can be within AZ, Cross AZ or Cross Region
- Replication is async -> reads are eventually consistent
- Replicas can be promoted to their own db

#### RDS read replicas - network cost

- Normally, in AWS there's a cost when data goes from one AZ to another, HOWEVER...
  - for some managed services this doesn't happen
  - for RDS read replicas WITHIN THE SAME REGION, no extra cost

- same region, different AZ = no cost
  - us-east-1a -> us-east-1b
  - async replication for free -> SAME REGION

- cross region = extra cost
  - us-east-1a -> eu-west-1b
  - async replication costs extra -> CROSS REGION

### Multi AZ = Disaster recovery

- Sync replication
- One DNS name - automatic app failover to standby
- Increased availability
- Failover in case of..
  - loss of AZ
  - loss of network
  - instace or storage failure

- No manual intervention in apps
- NOT USED FOR SCALING, but for AVAILABILITY and fault tolerance

```
            application
        writes  | ^
                v |  reads
        ---- one DNS ----
RDS db      <---- sync              RDS master db
instance          replication       instance
standy by                           (AZ A)
(AZ B)
```

> Read replicas can be setup as Multi AZ for DR (Disaster recovery)

#### From Single-AZ to Multi-AZ

- Zero downtime operation, meaning no need to stop the DB
- Just click on "modify" for the db
- What happens internally?
  - Snapshot is taken
  - A new db is restored from the snapshot in a new AZ
  - Sync is established between the two dbs

## RDS Custom for Oracle and Microsoft SQL server

- RDS custom: managed Oracle and Microsoft SQL server db with OS and db customization
- RDS: Automates setup, operation, and scaling of db in AWS
  - entire db and OS managed by AWS
- Custom: access the underlying db and OS, thus, we can:
  - config settings
  - install patches
  - enable native features
  - access the underlying EC2 instance using SSH or SSM session manager
  - full admin access to the underlying OS and the db

> While default RDS doesn't allow accessing the underlying EC2 instance, the custom does

- Best practices
  - De-activate automation mode to perform the customization
  - take a snapshot of db before

## RDS Proxy

- A proxy that sits between your applications and your RDS/Aurora dbs
  - avoids your db not getting overwhelmed by too many active connections
  - supports RDS and Aurora
    - RDS: mysql, postgres, mariadb, ms sql server
    - aurora: mysql and postgres
  - no code changes required
  - Allows apps to pool and share db connections with the db
  - Fully managed db proxy for RDS
  - Serverless, auto-scaling, highly available (multi-AZ)
  - Reduced RDS/Aurora failover time by 66%
- Improves db efficiency by reducing the stress on db resources (CPU/RAM) and minimize open connections (and timeouts)
- Enforce IAM authentication for db, and securely store credentials in AWS secrets manager
- RDS proxy is never publicly available, it must be accessed from VPC

### What problems does it solve?

- Relational dbs are resource-intensive when establishing connections
  - every open connection consumes a chunk of memory/CPU on the db server
- this is especially true when using Lambda or rapidly auto-scaling microservices

### Benefits

- Connection pooling and multiplexing: rds proxy maintains a small pool of warm established connections to the db
  - thousands of client requests share and reuse them
  - this way, they don't need to open/close new connections
- Faster failovers
- Enhanced security
  - enforce IAM authentication between application and RDS proxy
  - proxy connects to the db using credentials stored in AWS secrets manager
- No code rewrite: application connects to the proxy's endpoint as if it were the direct db connection

### When to use it?

- Serverless architecture (AWS lambda + RDS / Aurora): lambda spike causes `too many connections` db errors
- Unpredictable web traffic
- Enforcing zero-downtime failover

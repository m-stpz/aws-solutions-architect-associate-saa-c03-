# Aurora

- It's proprietary technology from AWS (not open source)
- Postgres and MySQL are both supported as Aurora db
  - drivers will work as if Aurora was a postgres or mysql db
- Aurora is "aws cloud optimized", meaning (it claims):
  - 5x performance improvement over MySQL on RDS
  - 3x performance over Postgres on RDS
- Aurora storage automatically grows in increments of 10gb, up to 256tb
  - it can have up to 15 replicas
  - replication process is faster than MySQL (sub 10ms replica lag)
  - failover is instantaneous. High-availability native
- Aurora costs more than RDS (20% more), but it's more efficient

## Aurora high availability and read scaling

- When data is saved to Aurora, the underlying storage layer distributes 2 physical copies of that data in eac of 3 separate AZs
  - AZ 1: copy A, copy B
  - AZ 2: copy C, copy D
  - AZ 3: copy E, copy F
    - Quorum model: 6 copies of data across 3 AZs
    - 4 copies out of 6 needed for writes: to confirm a write (commit a transaction), db only ways until any 4 storage nodes acknowledge the write
    - 3 copies out of 6 needed for reads: needs acknowledgement from at least 3 copies
    - self-healing with peer-to-peer replication
  - storage is striped across 100s of volumes: aurora doesn't store your db on a single virtual disk (like traditional EBS volume)
    - instead, it chops the data into small, manageable chunks and distributes them across a massive fleet of storage drives throughout AWS data centers
- One aurora instance takes writes (master)
- Automated failover for master in less than 30s
- Master + up to 15 aurora READ replicas serve reads
  - only ONE master though
- Support for cross region replication

## Advanced concepts

1. Replicas auto scaling: dynamically adjusts the number of read replicas in response to workload changes
   - write endpoint -> master [writer]
     - auto scaling doesn't touch the write instance, only adjusts the reader nodes to distribute query traffic
   - reader endpoint -> read replicas
     - as the reader endpoint starts receiving more requests and the read replicas CPU usage increases, new read replicas will be spun
     - these new replicas will be added to the reader endpoint, so they can be accessed
     - since these instances share the same distributed underlying storage volume, the new replicas don't need to replicate or copy a lot of disk data
       - they spin up and start serving traffic within minutes

2. Custom endpoints: allows us to create a dedicated DNS endpoint that routes queries to a specific subset of db instances, rather than all of them
   - by default, Aurora cluster provides a write endpoint (points to the single primary db) and a reader endpoint (load balances across all read replicas)
   - define a subset of aurora instances as a custom endpoint
     - ex: read analytical queries on specific replicas
   - reader endpoint is generally not used after defining custom endpoints
     - once we setup a custom endpoint, the reader endpoint is rendered basically useless
       - why? because the reader endpoint load balances connections indiscriminately across ALL available read replicas
       - if application continue using the generic reader endpoint, the entire purpose of the custom endpoint is rendered useless
     - then, you need to specify the other endpoints explicitly

3. Aurora serverless
   - automated db instantiation and auto-scaling based on actual usage
   - good for infrequent, intermittent or unpredictable workloads
   - no capacity planning needed
   - pay per second, can be more cost-effective

4. Global aurora
   - aurora cross region read replicas:
     - disaster recovery
     - simple to put in place
   - aurora global db (recommended):
     - 1 primary region (read / write)
     - up to 10 secondary (read-only) regions: we can replicate the db to up to 10 other geographic AWS region
       - replication lag is less than 1 second
     - up to 16 read replicas per secondary region: inside each of the secondary regions, there can be up to 16 reader db instances
       - 10 secondary regions x 16 read replica per region = 160 read instances globally
     - reduced latency
     - promoting another region (for DR [disaster recovery]) has an RTO of < 1min
     - **typical cross-region replication takes less than 1 second**

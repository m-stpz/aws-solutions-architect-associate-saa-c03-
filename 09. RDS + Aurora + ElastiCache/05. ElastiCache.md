# ElastiCache

- What RDS is for managed relation dbs, ElastiCache is for managed cache dbs (Redis/Memcached)
  - Since it's managed, AWS takes care of:
    - os maintenance / patching
    - optimizations
    - setup and config
    - monitoring, failure recovery and backups
- Cache: in-memory dbs with high performance and low latency
  - helps reduce the load of primary db by storing commonly used results
  - reduces loads of dbs for read intensive workloads

> Using ElastiCache, differently from the RDS proxy, which is basically just turning it on, demands significant code chances

## ElastiCache Architectures

### 1. DB Cache

- Application queries ElastiCache, if not available, get from RDS then store it on ElastiCache
  - Cache hit/miss
- Helps relieve load in RDS

> Cache must have an invalidation strategy to make sure only the most current data is used -> cache invalidation

```

application ---> cache hit      | elasticache

            ---> cache miss
                - read from db ---->  | amazon rds
                - write to cache
```

### 2. User session store

How to make application stateless...

- User logs into any of the application instances
- The application instance writes the session data into ElastiCache
- The user hits another instance of the application
- The instance retrieves the session from the cache

```
     --> applicationInstance1 -- write session --> | amazon
user --> applicationInstance2 -- read session ---> | ElastiCache
     --> applicationInstance3
```

## Redis vs Memcached

1. Redis: think of replication
   - Multi AZ with auto-failover
   - read replicas to scale reads and have high availability
   - data durability using AOF (append-only file) persistence
     - persistency guaranteed through an append-only log file
   - backup and restore features
   - supports sets and sorted sets
2. Memcached: think of sharding
   - multi-node for partitioning of data (sharding)
   - no high availability (replication)
   - non persistent
   - backup and store, only on serverless
   - multi-threaded architecture, good for performance

> When creating a ElastiCache, you might see Valkey, which is a replacement for Redis

## Cache security

- ElastiCache supports IAM authentication for Redis
- IAM policies on ElastiCache are used for AWS API-level security
- Redis AUTH
  - set password/token when creating the cluster
  - extra level of security for the cache, on top of security groups
  - supports SSL in-flight encryption
- Memcached
  - supports SASL-based auth (advanced)

## Patterns for ElastiCache

1. Lazy loading (cache-aside): data is only added to the cache on cache miss

- on demand when requested by read operation

```
[ Application Read Request ]
          │
          ├─► 1. Check ElastiCache
          │        ├── Cache Hit  ──► Return cached data immediately
          │        └── Cache Miss ──► 2. Query RDS/Database
          │                                  │
          │                           3. Write to Cache (with TTL)
          ▼                                  │
[ Return Data to Client ] ◄──────────────────┘
```

Pros

- efficient memory usage: no wasted RAM on unread records
- node resilience: if cache node fails/restarts, the application doesn't crash
  - it only experiences cache miss

Cons

- cache miss penalty: the very first request demands 3 round trips, thus increasing latency
  - cache check
  - db query
  - cache write
- stale data risk: if data is updated in the db, cache can serve outdated data until TTL expires

2. Write through: data is written to cache at the same time as it's written to the primary db

```
[ Application Write / Update Request ]
          │
          ├──► 1. Write to Database (RDS)
          └──► 2. Write / Update ElastiCache
```

Pros

- no stale data: cache is always in sync with db
- no read penaly

Cons

- write latency penalty: every write requires 2 network calls
  - db write
  - cache write
- cache pollution: writes populate the cache even if the record isn't read again, wasting memory
- node failure impact

3. Session store: elasticache acts as a centralized, shared session repo, thus making your app layer stateless
   - stateless compute: seamless auto scaling, meaning instances can scale up/down without logging users out/dropping shopping carts
   - no sticky session needed: eliminates the need for ALB sticky sessions, what prevents unenven load balancing across backend nodes

```
                     ┌──────────────────────┐
                     │   Load Balancer      │
                     └──────────┬───────────┘
                                │
            ┌───────────────────┴───────────────────┐
            ▼                                       ▼
   [ EC2 / Container A ]                   [ EC2 / Container B ]
            │                                       │
            └───────────────────┬───────────────────┘
                                │ (Read / Write Session via SessionID)
                                ▼
                   ┌─────────────────────────┐
                   │  ElastiCache (Redis)    │
                   │  Session Store + TTL    │
                   └─────────────────────────┘
```

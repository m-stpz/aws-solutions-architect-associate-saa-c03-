# My Clothes

- Allows people to buy clothes online
- There's a shopping cart
- Hundreds of users at the same time
- Scale, maintain horizontal scalability and keep web application as stateless as possible
- Users should:
  - not lose their shopping carts
  - have their details (address, etc) in a db
- This is stateful application

```
 ----------- route 53
 |              |            | ASG      |
user           ELB           | [az1] m5 |
            multi AZ         | [az2] m5 |
                             | [az3] m5 |
```

## Problem

When the ELB navigates from one instance to the other, the shopping cart is lost

- why?
  - request 1: ELB connects with instance on az1, create the shopping cart
  - request 2: who says it's going to go to the same instance? Possibly it won't. Thus, shopping cart is lost

### solution 1: stickiness [session affinity]

- this way, all user requests will go to the same instance
- this, however, still brings some problems
  - what if that instance goes down? Shopping cart is lost! [again]

### solution 2: user cookies

- instead of the ec2 instance storing the shopping cart, the user stores it
  - this way, the ELB can send the user to different ec2 instances, and the shopping cart is preserved
    - server is stateless and we were able to solve it without stickiness
  - the customer sends the necessary info on each request
  - seems good, but there are downsides:
    - http requests are now heavier
    - cookies can be tempered
      - thus, they need to be validated
    - they must be less than 4kb, so there's not much info that we can store on them

### solution 3: server session

- we saw that even though cookies can be used in order to keep our servers stateless, at the same time that we have a "shared" session between the servers, there are some downsides
  - for a shopping cart the cookies would likely be more than fine, however, for more sensitive information, we can use a server session [ElastiCache or also DynamoDB]
  - it basically allows us to store relevant information to a cache through the EC2 instances
    - customerid + shopping cart, for instance
    - when the client adds an item to the cart, we send this info the ec2, then the ec2 writes it to the cache
      - client action -> ec2 instance -> writes to -> elasticache
    - now, another ec2 instance can read from the elasticache whenever needed
      - client action -> ec2 instance -> reads from -> elasticache

- this is more secure than using cookies

```
 ----------- route 53
 |              |            | ASG      |   elasticache
user           ELB           | [az1] m5 |   - store/retrieve session data
            multi AZ         | [az2] m5 |
                             | [az3] m5 |   also: dynamodb [alternative]
```

### solution 4: storing user data in a db

- same thing as the previous solution [server session - elasticache], but now, we store it in the db [rds]

## Problem

- We're having a lot of users and the reads to writes ratio is rather big
- What should we do?
  - we need to scale the reads

- How?
  - 1. RDS [master writes] + RDS read replicas
    - we can have up to 15 RDS read replicas
  - 2. lazy loading: using a cache. Reduces the load on the db and increases performance, however, now it needs cache maintenance [what should be done application side]
    - store the info on cache
      - cache hit?
        - then, retrieve this info
      - cache miss?
        - check the db, return the info, then write it to cache

## Problem

- We had an issue that our system went down due to the AWS infra coming down. What to do?
  - We need better disaster recovery -> surviving disasters

- Route 53 is already multi az
- ELB should be multi az
  - it's not multi az by default
  - we must explicitly configure it as such
    - select subnets in at least >= 2 AZs when provisioning the LB
- ASG should be multi AZ
  - az1: N ec2 instance(s)
  - az2: N ec2 instance(s)
- RDS should be multi AZ
- ElastiCache, if used with redis (and valkey), can be multi az

> Multi-AZ is high availability [HA]: solutions above protect against an AZ failure
> True DR requires MULTI-REGION: surviving a regional outage requires a multi-region architecture

## Problem

- We want to make our application as safe as possible, how can we do it?

1. from user to our ELB, open HTTP/HTTPS from everywhere [0.0.0.0/0]
   - user --- http/https everywhere [0.0.0.0/0] --- elb
   - internet-facing ELB accepts public traffic
   - its SG [ELB-SG] allows inbound ports 80 (HTTP) and 443 (HTTPS) from everywhere

2. from ELB to ASG/ec2: only traffic from ELB gets to the ASG/ec2 instances
   - ELB --- security group --- EC2
   - EC2 instances can't be directly reachable from the internet
   - their SG [APP-SG], the inbound rule allows application traffic with the source set to `ELB-SG`
     - meaning that the port doesn't matter, what matters is the source [service's identity]

```
[ ELB ] ──(Picks random client source port: 49215)──► Knocks on ──► [ EC2 Instance ]
                                                                      Listening on: Port 80
                                                                      Security Group says:
                                                                      "Allow traffic to PORT 80
                                                                       if it originates from ELB-SG"
```

3. from EC2 to ElastiCache: only traffic from EC2 gets to the ElastiCache
   - EC2 --- security group --- ElastiCache
   - its SG `Cache-SG`, the inbound rule allows port 6379 (Redis) with the source set to `App-SG`

4. from EC2 to RDS: only traffic from EC2 gets to the RDS
   - EC2 --- security group --- RDS
   - its SG `DB-SG`, the inbound rule allows the db port with the source set to `App-SG`

```
[ Internet: 0.0.0.0/0 ]
          │
          │ Inbound: 80 / 443 | Source: 0.0.0.0/0
          ▼
┌───────────────────────────────┐
│     ELB Security Group        │ (ID: sg-elb123)
└──────────────┬────────────────┘
               │
               │ Inbound: Port 8080 | Source: sg-elb123
               ▼
┌───────────────────────────────┐
│     EC2 Security Group        │ (ID: sg-app456)
└───────┬───────────────┬───────┘
        │               │
        │ Port 6379     │ Port 5432 / 3306
        │ Source:       │ Source:
        │ sg-app456     │ sg-app456
        ▼               ▼
┌──────────────┐ ┌──────────────┐
│ ElastiCache  │ │     RDS      │
│  Sec. Group  │ │  Sec. Group  │
└──────────────┘ └──────────────┘
```

# Auto scaling group [ASG]

- Load of websites and applications can change
- In the cloud, we can create/remove servers quickly

- The goal of auto scaling group (ASG) is to:
  - scale out (add EC2 instances) to match increased load
  - scale in (remove EC2 instances) to match decreased load
  - ensure a minimum and maximum number of EC2 instances running
  - AUTOMATICALLY REGISTER new instances to LB
  - Re-create an EC2 instance in case a previous one is terminated (ex: if unhealthy)

- ASG are free, we only pay for the underlying EC2 instances

```
|----| mininum capacity [ex: 2 instances]
|--------| desired capacity [ex: 4 instances]
|------------| maximum capacity [ex: 7 instances]
```

- Also, the ELB can inform the ASG which instances are unhealthy and the ASG can terminate the instances that are deemed unhealthy by the ELB

> It's a great combination using an ELB and a ASG

## ASG attributes

- A launch template (previously called "launch configurations")
  - AMI + instance type
  - EC2 user data
  - EBS volumes
  - Security groups
  - SSH key pair
  - IAM roles for EC2 instances
  - Network + subnet information
  - LB info
- Min / max size / initial capacity
- Scaling policies

### Scaling policies + CloudWatch

- It's possible to scale out/in an ASG based on CloudWatch alarms
- An alarm monitors a metric (ex: average CPU, custom metric)
  - Metrics such as average CPU are computed for the overall ASG instances
- Based on the alarm, we can create scale `___` policies for `___` the number of instances
  - out/up -> increase
  - in/down -> decrease

## ASG and ELB

- The relationship between ELB and ASG is built around the **Target Group**
- The target group acts as a bridgem connecting traffic distribution (ELB) with dynamic compute management (ASG)
  - ELB routes the traffic: distributes incoming client requests across available, healthy instances
  - ASG manages the capacity: adds/removes EC2 instances dynamically based on demand or instance health
  - Target group is the shared directory: holds the list of instances that the ELB routes to and ASG modifies

```
                     ┌──────────────────────┐
                     │   Load Balancer      │  ◄── Receives incoming client traffic
                     └──────────┬───────────┘
                                │ (Routes to)
                                ▼
                     ┌──────────────────────┐
                     │     Target Group     │  ◄── The bridge & health monitor
                     └──────────▲───────────┘
                                │ (Registers / Deregisters instances)
                                │
                     ┌──────────┴───────────┐
                     │  Auto Scaling Group  │  ◄── Launches / Terminates EC2 instances
                     └──────────────────────┘
```

### How they work together

- Scale-out (traffic increases):
  - ASG launches a new EC2 instance and automatically registers its ID with the target group
  - Once ELB's health check pass, LB starts sending traffic to it
- Scale-in (traffic decreases):
  - ASG initiates instance termination
  - ELB triggers deregistration delay / connection draining
    - finish active requests, deregisters the target, and ASG terminates the instance
- Self-healing (ELB health check integration)
  - By defeault, ASG only monitors EC2 hardware status (running/stopped)
  - If you enable ELB health checks on the ASG, the ASG will automatically replace instances if the load balancer's application endpoint check fails
- Target tracking scaling: The ASG can scale up/down based on metrics emitted by the load balancer
  - e.g. maintaining an `ALBRequestCountPerTarget` target

# Network Load Balancer

- Network load balancers (layer 4) allow to:
  - Forward TCP & UDP traffic to your instances
  - handle millions of requests per second
  - ultra-low latency

- NLB has one static IP per AZ and supports assigning Elastic IP
  - helpful for whitelisting specific IP

- NLB are used for extreme performance, TCP or UDP traffic [also static IPs]

- Health checks performed by NLB target groups support: TCP, HTTP, and HTTPS protocols
- For NLB we also attach security groups

```
[ Internet / Public Clients ]
              │
              ▼ (1. Inbound to LB)
   ┌──────────────────────┐
   │ Load Balancer (ALB)  │ ◄─── Attached to [ Load Balancer Security Group ]
   │                      │      (Allows Port 80/443 from 0.0.0.0/0)
   └──────────┬───────────┘
              │
              ▼ (2. Evaluates Listeners & Rules)
   ┌──────────────────────┐
   │     Target Group     │ ◄─── Logical grouping + Health Check config
   └──────────┬───────────┘
              │
              ├───────────────────────────────┐
              ▼ (3. Forward to Target)        ▼ (3. Forward to Target)
   ┌──────────────────────┐       ┌──────────────────────┐
   │     EC2 Instance     │       │     EC2 Instance     │
   │                      │       │                      │
   │  [ EC2 Instance SG ] │       │  [ EC2 Instance SG ] │
   │  Inbound: Port 80    │       │  Inbound: Port 80    │
   │  Source: alb-sg-id   │       │  Source: alb-sg-id   │
   └──────────────────────┘       └──────────────────────┘
```

- LB security group (front door guard): filters traffic before it touches the load balancer
- Load balancer: entry point after the LB security group
- Target group (routing and health): a logical container managed by the LB
  - LB forwards traffic to the target group
  - target group performs health checks on the registered endpoints
- EC2 instance (the workers): the actual compute
- EC2 security group (backend guard): protects the instances from unauthorized access
  - its inbound rules sets the source to the LB's security group id
    - this way, only traffic that came from the LB passes through

## ALB vs NLB

| Feature             | ALB                                                      | NLB                                                |
| ------------------- | -------------------------------------------------------- | -------------------------------------------------- |
| OSI Layer           | layer 7 (application)                                    | layer 4 (transport)                                |
| Supported protocols | HTTP, HTTPS, HTTP/2, gRPC, Websockets                    | TCP, UDP, TLS                                      |
| Routing logic       | URL path, host header, query strings, headers            | IP, port, protocol                                 |
| Latency             | low (5-20ms due to payload inspection)                   | Ultra-low / sub-millisecond                        |
| Throughput/scaling  | Scales dynamically (needs pre-warming for sudden bursts) | Handles millions of RPS instantly (no pre-warming) |
| Static/Elastic IP   | No, uses dynamic DNS name only                           | Yes, one static IP per AZ                          |

### When to use ALB

- Microservices and web applications
- Container workload
- Security and WAF integration
- HTTP/2, gRPC, and websockets

### When to use NLB

- Extreme performance and ultra-low latency: latency-sensitive workloads
  - gaming servers, high-frequency trading, real-time media streaming
- non-http protocols: applications running on TCP, UPD or custom binary socket protocols
- static IP / whitelisting requirements: clients or corporate firewalls require fixed, unchanging IP addresses to whitelist your service
- sudden, massive spikes: spikes that would outpace ALB
- end-to-end TLS pass-through: compliance demands encryption directly to the backend target without the load balancer decrypting the traffic

# SSL/TLS certificates

- SSL certificate allows traffic between clients and load balancers
  - they an encrypted in transit (in-flight encryption)

- SSL = Secure Sockets Layer, used to encrypt connections
- TLS = Transport Layer Security, newer version
  - Nowadays, TLS is mainly used, but people still refer as SSL

- Public SSL are issued by Certificate Authorities (CA)
  - Comodo, GoDaddy, Symantec, Letsencrypt, etc

- SSL certificates have a expiration date and must be renewed

```
      https                 http
      encrypted           over private VPC
Users <------------> LB <------------> EC2 instance

- SSL termination
```

- LB uses an X.509 certificate (SSL/TLS server certificate)
- Certificates are managed using ACM (AWS Certificate Manager)
- Create/Upload your own certificates

- HTTP Listener:
  - specify a default certificate
  - add optional list of certs to support multiple domains
  - Clients can use SNI (server name indicator) to specify the hostname they reach
  - Ability to specify a security policy to support older version of SSL/TLS (legacy clients)

## Why do you need it?

- Enables HTTPS and provides:
  1. encryption in transit: encrypts data moving between the user's browser and your backend (passwords, credit cards, auth tokens, session tokens)
  - prevents man-in-the-middle (MITM) snooping
  2. authentication and trust: digitally proves your server actually owns the domain
  - without it, modern web browsers will show a warning and search engines will penalize your rankings

## Where do you put it?

- In modern cloud architecture, almost always it's on the LB

| Pattern                    | Where cert lives        | Traffic path                                    | best used for                                               |
| -------------------------- | ----------------------- | ----------------------------------------------- | ----------------------------------------------------------- |
| SSL termination (standard) | LB only                 | Public HTTPS -> LB -> Internal HTTP -> EC2      | most web apps. Offloads CPU-intensive crypto from instances |
| End-to-end encryption      | Both LB and EC2         | Public HTTPS -> LB -> Re-encrypted HTTPS -> EC2 | strict compliance requirements                              |
| SSL pass-through           | EC2 only (requires NLB) | Public TCP/TLS -> NLB -> HTTPS -> EC2           | when LB must never decrypt the payload                      |

## SNI (Server Name Indication)

- What does it do?
  - Solves the problem of loading multiple SSL certificates onto one web server (to serve multiple websites)

- Server Name indication allows a SINGLE server, or LB, to HOST MULTIPLE domain names
  - Why would you want to host multiple domains on a single server?
    - 1. cost optimization: hosting multiple lower-traffic sites onto a single server
    - 2. microservices and multi-tenant SaaS: a client have get a custom branded domain
    - 3. operational simpliciy: management of a consolidated chunk is easier than isolated, fragmented environments for every separate URL

- It's a "newer" protocol and requires the client to indicate the hostname of the target server in the initial SSL handshake
- Server then finds the correct certitificate, or returns the default one

- SNI only works for ALB, NLB, and CloudFront
  - doesn't work for CLB

## LB and SSL/TLS certificates

- CLB
  - supports only one SSL certificate
  - Must use multiple CLB for multiple hostname with multiple SSL certificates
- ALB and NLB
  - Supports multiple listeners with multiple SSL certificates
  - Users SNI to make it work

# Security groups

- Security groups are fundamental of network security in AWS
- The control traffic into or out of our EC2 instance

```
                                 |
client ---> inbound traffic ---> | security group | ec2 instance |
       <--- outbound traffic <-- |
```

- They contain `allow` rules
- They can reference by IP or by other security groups
- They act as a "firewall" on our EC2 instances
- They regulate:
  - access to ports
  - authorized IP ranges - IPv4 and IPv6
  - control of inbound/outbound network/access
    - other -> instance
    - other <- instance

- A table of it usually has:
  - type
  - protocol
  - port tange
  - source
  - description

- A security group can be attached to many instances and an instance have have multiple security groups
  - N to N relationship

- By default, all `____` traffic is `____`
  - inbound / blocked
  - outbound / allowed

- Every time we see a timeout when trying to access an EC2 instance, it's a security group issue

## Classic ports

- 22 = SSH (secure shell): log into a linux instance
- 21 = FTP (file trasfer protocol): upload files into a file share
- 22 = SFTP (secure file transfer protocol): upload files using SSH
- 80 = HTTP - access unsecured websites
- 443 = HTTPS - access secured websites
- 3389 = RDP (remote desktop protocol): log into a windows instance

## EC2 [VM] vs Serverless [Lambda]

- EC2 we control the virtual servers
- Serverless we outsource the infra management to AWS

| Feature               | EC2 (Virtual machine)                                                                    | AWS Serverless (e.g, lambda)                                  |
| --------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Server management     | I manage OS updates, security patches, deps, and network rules                           | AWS handles all OS maintenance, runtime updates, and hardware |
| Billing model         | Pay for uptime. Each second the VM is running, whether traffic hits it or not            | Pay per execution. Pay strictly per request and its duration  |
| Execution limit       | No execution limit, processes can run 24/7                                               | Hard execution timeout (max 15 minutes per request on lambda) |
| Scaling               | Scales via auto scaling groups (1-3 minutes to boot new VMs)                             | Instantly from 0 to thousands of concurrent executions in ms  |
| State and connections | Stateful: supports persistent connections (websockets, long-polling, background workers) | Stateless: functions start up, do their job, and terminate    |

## When to use EC2s

- EC2s are great for when you need:
  - continuous compute power
  - custom hardware/OS config
  - predictable performance

- Meaning:
  - high, steady-state traffic
  - long-running & compute-heavy tasks
  - low-latency & real-time servers
  - dbs and caches
  - legacy monoliths

- EC2 are one of the most common ways companies deploy microservices
  - normally, however, microservices on ec2 are typically containerized using docker and managed by an orchestrator

## SG Inbound Rule

- Works as a virtual firewall attached to an AWS resource (its ENI - Elastic Network Interface)
- It inspects every incoming packet and deciddes whether to let it reach the OS
- Refers to the DESTINATION PORT listening on the service itself

```
┌───────────┬──────────────┬────────────────────────┬───────────────────────────┐
│   Type    │   Protocol   │       Port Range       │          Source           │
│  (Label)  │  (TCP/UDP)   │  (Destination on host) │    (Who is allowed in)    │
└───────────┴──────────────┴────────────────────────┴───────────────────────────┘
```

- port range: the destination port -> the port that the service on the server is listening
- source: the sender's NI identity
